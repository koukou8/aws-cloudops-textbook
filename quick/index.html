VPCフローログ

VPCのネットワーク通信を、「どこから・どこへ・許可／拒否」で記録するログ。

まず、この3つ

  • 送信元・宛先IP、ポート、プロトコル、通信量などを記録する。通信の中身は記録しない。
  • VPC・サブネット・ENI単位で設定できる。CloudWatch LogsやS3などへ配信する。
  • ACCEPTは通信が許可された記録。アプリの処理成功を保証しない。

ログの使い分け

知りたいこと主に使うもの
IP通信が許可・拒否されたかVPCフローログ
誰がAWSの設定を変更したかCloudTrail
CPUやアプリの状態はどうかCloudWatchのメトリクス・ログ

判断のポイント

REJECTなら、まずSG・NACLを確認。ACCEPTでも接続できなければ、OS・待受ポート・アプリなども調べる。TCPはプロトコル番号6、UDPは17。

確認：フローログからHTTPリクエストの本文を読める？

読めません。IP通信のメタデータを調べるログであり、ペイロードの記録ではありません。

参照：AWS公式 · VPCフローログ

詳しい教材 ↗

Amazon ElastiCache

よく使うデータをメモリに置き、応答を速くし、DBの負荷を減らすサービス。

まず、この3つ

  • キャッシュにあればHIT。なければMISSとしてDBから取得し、キャッシュへ保存する（Cache-Aside）。
  • アプリ側で読み書きを組み込む。DBの前に置くだけで自動的に高速化するわけではない。
  • Valkey・Redis OSS・Memcachedなどのエンジンがある。使うデータ構造や可用性の要件で選ぶ。

混同しやすい3つ

仕組み役割
TTLデータの有効期限。鮮度とヒット率に影響する
シャードデータを分割し、容量や処理を分散する
レプリカコピーを保持し、読み取り分散や可用性に使う

判断のポイント

キャッシュが消えても困らない設計に。DBなどから再取得できるようにし、期限切れが集中してDBへ負荷が戻ることにも備える。

確認：TTLを長くすれば、いつでも正しい最新データになる？

いいえ。ヒット率は上がる可能性がありますが、古い値が残りやすくなります。更新時の削除・再設定も設計します。

参照：AWS公式 · ElastiCache

03 / GOVERNANCE

詳しい教材 ↗

AWSのリソース上限

作れる数・使える量の上限を「サービスクォータ」という。上限の適用単位が重要。

まず、この3つ

  • 多くはアカウント×リージョン単位。ただしVPC単位・AZ単位など、リソースによって異なる。
  • 引き上げを申請できる上限と、変更できない上限がある。申請しても即時反映とは限らない。
  • CloudFormationも各サービスの上限に従う。失敗時はスタックのイベントと対象サービスの使用量を見る。

VPC関連の代表例

リソースデフォルト値と単位
VPC5 ／ アカウント・リージョン
サブネット200 ／ VPC
NATゲートウェイ5 ／ AZ
Elastic IP（EC2-VPC）5 ／ アカウント・リージョン

代表的なデフォルト値。実際の適用値はService Quotas等で確認する。

画像の設問なら

同じアカウント・同じリージョンでVPCを増やし続けて失敗 → VPC数の上限を疑う。テンプレートが同じでも、既存リソースの使用量は増えている。

確認：東京リージョンのVPC数が上限なら、大阪でも作れない？

いいえ。VPC数のクォータはリージョンごとです。ただし大阪側でも、そのアカウントに適用された上限と使用量の確認は必要です。

参照：AWS公式 · Amazon VPCのクォータ

04 / OPERATIONS

詳しい教材 ↗

AWS Systems Manager

多数のサーバーに対する操作・パッチ適用・状態確認をまとめて行う運用サービス。

まず、この3つ

  • 管理対象にするには、SSM Agent・必要なIAM権限・サービスへのネットワーク接続などを整える。
  • タグで対象を選ぶ。パッチベースラインは「どのパッチを承認するか」のルール。対象の選択とは別。
  • Scanは調査、Installは適用。適用後はパッチのコンプライアンス状況を確認する。再起動も考慮する。

どの機能を使う？

機能担当すること
Run Commandコマンドやスクリプトを複数台へ実行
Patch Managerパッチのスキャン・適用・適用状況の確認
Maintenance Windows定期的な作業時間帯とタスクの設定
Session ManagerSSHの受信ポートを開けずに対話的に接続

画像の設問なら

80台へ今すぐ適用＋以後も自動化＋レポート → Patch Manager。ベースラインを定め、タグで対象を選び、今後の適用はメンテナンスウィンドウなどで定期化する。

確認：Run Commandがパッチベースラインを作る機能？

いいえ。ベースラインを管理するのはPatch Managerです。Run Commandはパッチ用ドキュメントの実行にも使われますが、役割を区別します。

参照：AWS公式 · Patch Manager

05 / AUDIT

詳しい教材 ↗

AWS CloudTrail

AWSで「誰が・いつ・何を操作したか」を追跡する、監査のための記録。

まず、この3つ

  • イベント履歴では、過去90日間の管理イベントをリージョンごとに確認できる。
  • 継続保存には証跡などを設定する。S3オブジェクト操作などのデータイベントは、別途記録対象に設定する。
  • ログファイルの整合性検証を有効にすると、署名付きダイジェストを生成。ログの改変や削除の検出に使う。

守る目的が違う

仕組み主な目的
ログファイルの整合性検証保存後の変更などを検出する
S3 Object Lock保持期間中の上書き・削除を制限する
暗号化（KMSなど）データを不正に読まれにくくする

画像の設問なら

ログの真正性を検証したい → CloudTrailの整合性検証。自作Lambdaでハッシュを保存する必要はない。ただし、有効化だけで自動監視が完了するわけではなく、CLI等で検証を実行する。

確認：整合性検証を有効にすると、ログを書き換えられなくなる？

いいえ。これは改変の「検出」のための仕組みです。削除・上書きの防止には、権限制御やS3 Object Lockなどを組み合わせます。

参照：AWS公式 · ログファイルの整合性検証

06 / IDENTITY

詳しい教材 ↗

AWS IAM

AWSで「誰が・どのリソースに・何をしてよいか」を制御する仕組み。

まず、この3つ

  • 認証＝誰かの確認、認可＝何を許可するか。ログインできても、すべての操作ができるわけではない。
  • 必要な操作・対象だけを許可する最小権限が基本。ポリシーの明示的なDenyはAllowより優先する。
  • ロールは引き受けて利用し、一時的な認証情報で操作する。従業員ごとのIAMユーザー作成は必須ではない。

混同しやすい役割

仕組み答える問い
信頼ポリシー誰がこのロールを引き受けられる？
許可ポリシー引き受けたロールで何ができる？
SAML / SCIMSAMLは認証連携、SCIMはユーザー・グループの同期

画像の設問なら

LDAP → SAML IdP → STS → IAMロール。LDAPで認証するIdPを用意し、グループに応じてロールへ割り当てる。汎用LDAPをそのままIAM Identity Centerへ直接同期する案ではない。

確認：Direct ConnectでLDAPサーバーにつなげば、IAMとの認証連携も完成？

いいえ。Direct Connectはネットワーク接続です。認証情報をAWSへ連携するIdPや、ロールの信頼・許可設定が別途必要です。

参照：AWS公式 · SAMLフェデレーション

07 / COMPUTE

詳しい教材 ↗

AWS Lambda

イベントをきっかけにコードを動かす。サーバー基盤の管理はAWSに任せるサービス。

まず、この3つ

  • S3への保存やAPI要求などで起動する。利用者はコード・IAM権限・タイムアウトなどを設計する。
  • 同時実行数＝その瞬間に処理中の要求数。毎秒リクエスト数（RPS）とは異なる。
  • 平均同時実行数の目安は毎秒の到着数 × 平均処理時間（秒）。200件/秒 × 2秒なら約400。

400枠を「予約」するのはどれ？

設定役割
予約済み同時実行数関数専用の枠を確保し、同時に上限も設定
プロビジョンド同時実行数実行環境を事前初期化し、開始時の遅延を減らす
メモリ / DLQメモリは処理性能、DLQは失敗イベントの回収

画像の設問なら

他アプリに枠を奪われず400の容量を確保 → 予約済み同時実行数を400。この関数の上限も400になる。400個の環境を常時起動する設定ではなく、急増時の即時処理まで保証するものでもない。

確認：予約済み同時実行数を400にした関数は、暇なら500まで増えられる？

増えられません。400は専用に確保する枠であると同時に、その関数の上限です。余剰の共有枠を借りて500にすることはできません。

参照：AWS公式 · 同時実行数の設定
