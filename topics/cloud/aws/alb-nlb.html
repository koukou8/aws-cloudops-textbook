ALB / NLBの使い分け

どちらもアクセスを複数のサーバーへ分散するロードバランサー。違いは「何を見て、どこへ振り分けるか」です。

ALB · Application Load Balancer

HTTPの内容を見て振り分ける

URLのパス、ホスト名などに応じて転送先を変える、Webアプリの案内係です。

NLB · Network Load Balancer

TCP / UDPなどの通信を分散する

HTTPのパスを読まずに通信を転送します。独自プロトコルや固定IPの要件が選択の手掛かりです。

この教材で学べること

  • L4 / L7、リスナー、ターゲットグループの役割を説明する。
  • URL、TCP / UDP、TLS、固定IPの要件から構成を選ぶ。
  • 複数AZへの配置、ヘルスチェック、権限・通信制御を確認する。

基礎編：ロードバランサーの役割

1.1 アクセスの入口をまとめ、処理を分散する

ロードバランサー（Load Balancer）は、利用者からのアクセスを受け、複数の処理先へ分散します。AWSではElastic Load Balancing（ELB）というサービス群が提供し、ALBとNLBはその種類です。「ELBという別製品とALBを並べて選ぶ」という関係ではありません。

処理先はターゲットと呼び、EC2インスタンスなどを登録します。通常はヘルスチェックに合格したターゲットへ転送します。サーバー1台に直接アクセスを集中させる構成に比べ、負荷分散と可用性の向上を図れます。

01 利用者共通のDNS名に接続

どのサーバーが動いているかを個別に管理しない

02 ELBALB または NLB

接続を受け、ルールや通信情報から転送先を選ぶ

03 ターゲット複数AZのサーバー

登録先の状態を確認しながら処理を分散する

負荷分散と台数の増減は別です。ロードバランサーを作っただけでEC2の台数が増えるわけではありません。必要に応じてEC2 Auto Scalingなどと組み合わせます。

出典：ALBの概要と関連サービス

Q1. ELB、ALB、NLBの関係として正しいものは？

1.2 ALBはL7、NLBはL4

L7はOSI参照モデルのアプリケーション層です。ALBはHTTPリクエストを扱い、「/apiへの要求はAPIサーバー、/imagesへの要求は画像サーバー」のように振り分けます。ホスト名やHTTPヘッダーなども判断に使えます。

L4はトランスポート層です。NLBはTCP接続やUDPフローなどを分散します。HTTP以外の通信にも対応できますが、URLのパスを解釈して処理先を変えるものではありません。NLBでもHTTP/HTTPSの通信自体は運べます。

比較点ALBNLB
主な判断の層L7：HTTPリクエストL4：接続・フロー
リスナーのプロトコルHTTP / HTTPSTCP / TLS / UDPなど
パス・ホスト名による転送対応HTTPの内容による転送には非対応
固定IPの直接割り当て非対応。通常はDNS名で利用有効なAZごとに固定IP
AWS WAFの直接関連付け対応非対応
TLS終端HTTPSリスナーで対応TLSリスナーで対応
補足：NLBが対応するプロトコル
現行の公式資料ではTCP、TLS、UDP、TCP_UDPに加え、QUIC、TCP_QUICも記載されています。ここでは最初に覚える軸として、HTTPの内容を見るALBと、TCP/UDP等を扱うNLBを比較します。

出典：ALBリスナー、NLBリスナー、NLBの固定IP

Q2. UDPを使う独自のゲーム通信を分散したい。選ぶのは？

1.3 リスナー・ルール・ターゲットグループ

用語役割ALBの例
リスナープロトコルとポートを指定した入口HTTPS : 443
ルール条件と実行する処理/api/*ならapi-tgへ転送
ターゲットグループ転送先をまとめた単位api-tgにAPIサーバーを登録
ターゲット実際に処理する登録先EC2、IPアドレスなど

入口のポートと、サーバー側のポートは同じでなくても構いません。たとえばALBがHTTPSの443番で受け、ターゲットのHTTPの8080番へ転送する構成があります。この場合、443番で接続できるかと、8080番へ転送できるかは別々に確認します。

2

応用編：ルール・暗号化・固定IP

2.1 URLを変えたら、転送先はどう変わる？

ALBのルールには優先順位があります。小さい数値のルールから評価し、条件に一致した処理を行います。どれにも一致しない場合はデフォルトルールを使います。たとえば優先度10の/api/*、20の/images/*、最後に通常のWeb画面、という設定です。

振り分けの比較デモ

同じHTTPS要求でも、ALBはパスを読み、NLBのTCPリスナーは暗号化された通信をそのまま転送します。

01 入口ALB · HTTPS : 443
02 判定優先度10 · /api/*
03 転送先api-tg

ALBがHTTPSを復号し、パスに一致するAPI用グループへ転送します。

学習用の簡略モデルです。NLB側は1つの転送先グループを設定した例で、ターゲットの選択アルゴリズムや障害時の動きは再現していません。

出典：ALBのリスナールール

Q4. /apiと/imagesを別のサービスへ送り分けたい。適切なのは？

2.2 TLS終端とパススルーは別の構成

TLSは通信を暗号化する仕組みです。「TLS終端」は、その暗号化された接続をロードバランサーなどでいったん終えることです。ALBはHTTPSリスナー、NLBはTLSリスナーで終端できます。証明書はAWS Certificate Manager（ACM）などで用意します。

一方、NLBにTCPの443番リスナーを設定すると、TLSを復号せずバックエンドへ渡せます。これがTLSパススルーです。この場合、証明書と復号処理はバックエンドが担当します。

構成復号する場所見分けるポイント
ALB · HTTPSALBHTTPの内容を判定できる
NLB · TLSNLBTLSは終端するが、HTTPのパスルーティングはしない
NLB · TCP 443バックエンド暗号化された通信をそのまま渡す
「HTTPSだからALB」と即断しない。NLBでもHTTPSの通信を運べます。また、ALBでTLS終端してもバックエンドへの区間が自動的にHTTPSになるわけではありません。転送先グループのプロトコルも確認します。

出典：ALBのHTTPSリスナー、NLBのTLS終端とTCPパススルー

Q5. TLSをロードバランサーで復号せず、EC2で終端したい。選ぶ構成は？

2.3 固定IPとL7機能が両方必要なら

NLBは、有効化したアベイラビリティーゾーン（AZ）ごとに固定IPを持ちます。インターネット向けNLBでは、有効なサブネットごとにElastic IPを関連付けられます。「取引先のファイアウォールに接続先IPを許可登録する」といった要件が判断材料です。

ALBには固定IPを直接割り当てられません。固定IPとALBのパスルーティングを両立したい場合は、NLBのターゲットとしてALBを登録する構成が選択肢です。NLBの入口とALBのL7機能を組み合わせられますが、2つ分の構成管理や費用が必要になります。

01 固定の入口NLB · TCP 443

AZごとの固定IPを利用

02 Webの判断ALB · HTTPS 443

ここでTLS終端し、パスやホスト名を評価

03 サービスAPI / Webのグループ

各グループ内のサーバーへ分散

補足：NLB→ALBの前提とPrivateLink
この構成ではNLBとALBを同じAWSアカウント・同じVPCに配置し、ターゲットタイプalbのグループを使います。グループのプロトコルはTCPで、ポートはALBのリスナーに合わせます。PrivateLinkのエンドポイントサービスとALBのL7機能を組み合わせる用途にも使えます。

出典：NLBの固定IP、NLBの転送先としてALBを利用

3

実務編：安定して転送するために

3.1 複数AZと公開範囲を設計する

ALBだから公開用、NLBだから社内用、という区別ではありません。どちらにもインターネット向けと内部向けの構成があります。誰が入口に到達する必要があるかで選びます。

可用性のためには、ロードバランサーだけでなく、実際の処理先も複数AZに分散させます。入口が冗長でも、唯一の処理先が停止すれば業務を継続できません。ALBの通常のAZ構成では2つ以上のAZを選びます。NLBは1つのAZから作れますが、複数AZでの構成を検討します。

固定IPは「必ず1個」ではありません。NLBでは有効なAZごとに入口のIPがあるため、許可リストにも必要なIPを反映します。通常の接続先としてはDNS名を利用し、単一AZのIPだけに依存しない設計を考えます。

出典：ELBの仕組みとAZ、NLBのAZごとの動作

Q7. AZ障害への耐性を高める設計は？

3.2 ヘルスチェックは「実際に使えるか」を測る

ヘルスチェックのプロトコル、ポート、パス、成功とみなす応答を確認します。Webアプリなら、ヘルスチェック用のパスが認証を要求したり、想定外のリダイレクトを返したりすると、不健康と判定される原因になります。

NLBのアクティブヘルスチェックではTCP、HTTP、HTTPSを使います。UDPのサービスでも、UDPそのものでチェックするのではなく、別の対応するチェックを設定します。単にTCPポートが開いているだけでなく、必要ならUDPアプリの状態を反映する確認口を用意します。

注意：「全台unhealthyなら必ず転送しない」ではない
ALBやNLBには、すべてのターゲットが不健康な場合などに、正常性にかかわらず転送を試みるfail-openの動作があります。ヘルスチェックをアクセス制御の代用にせず、障害の検出・通知と復旧を設計します。

出典：ALBのヘルスチェック、NLBのヘルスチェック

Q8. NLBでUDPサービスの正常性を確認する方法は？

3.3 通信経路とセキュリティグループを確認する

「利用者→ロードバランサー」と「ロードバランサー→ターゲット」の両区間を確認します。リスナーの設定だけでなく、ターゲットの待受ポート、セキュリティグループ（SG）、ネットワークACL、ルートも関係します。ヘルスチェックのポートが別なら、その通信も許可します。

NLBにもSGを関連付けられます。ただし、SGなしで作成したNLBに、後から初めてSGを付けることはできません。作成時にSGを付けておけば、その後に関連付けを変更できます。「NLBはSG非対応」という古い説明に注意してください。

症状まず調べる場所
入口へ接続できないDNS、公開範囲、リスナー、SG・NACL、経路
ターゲットがunhealthyチェック用ポート・パス、応答、SG、アプリの待受
別サービスへ転送されるALBの条件、優先順位、デフォルトルール
APIの遅延が大きいLBとアプリ双方のメトリクス、処理時間、容量

追加演習：セッション維持とヘルスチェック

CloudFront → ALB → Stateful EC2

CloudFrontのキャッシュ／オリジンリクエストポリシーでセッションクッキーをALBへ転送し、ALBのターゲットグループ属性でスティッキーセッションを有効にします。設定単位はリスナールールではなくターゲットグループです。長期的にはセッションをElastiCacheやDBへ外部化し、インスタンス障害やスケールインでも状態を失わない設計が堅牢です。

ALBでターゲットがUnhealthy

最初にターゲットグループのHealthCheckProtocol／Port／Path／成功コードと、アプリが実際にその宛先で応答しているかを確認します。次にALBのセキュリティグループからターゲットへの許可、NACL、待受アドレス、起動時間を切り分けます。

NLBの固定IP要件：毎秒数百万のL4接続とAZごとの固定IPが必要ならNLBを選び、インターネット向けではサブネットごとにElastic IPを関連付けられます。
