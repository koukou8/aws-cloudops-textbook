基礎編：バックアップをポリシーで管理する

1.1 5つの構成要素

AWS Backupは、対応するAWSリソースのバックアップを集中管理するサービスです。バックアッププランにスケジュールや保持期間を定義し、タグまたはリソースIDで対象を選択します。作成された復旧ポイントはバックアップボールト（保管庫）へ保存されます。

「毎日取得」「28日保持」「別リージョンへコピー」といった要件はルールへ記述します。対象が増えたときは、たとえば Backup=Daily のタグで自動的に同じ方針へ参加させられます。

要素役割
バックアッププラン保護方針をまとめるコンテナ
バックアップルール頻度、開始時間、保持期間、コピー先を定義
リソース選択タグまたはIDで対象を指定
バックアップボールト復旧ポイントを保管し、アクセスを制御
復旧ポイント復元に使うバックアップ成果物

1.2 定期バックアップと継続バックアップ

定期バックアップは、決めた時刻にスナップショット型の復旧ポイントを作ります。復元できるのは取得時点です。継続バックアップは、対応するRDSリソースなどの変更履歴を保持し、保持期間内の指定時点へ戻すPITRを提供します。

AWS Backupで作成したRDSの定期バックアップはRDS側では手動スナップショットとして、継続バックアップは自動バックアップとして扱われます。継続バックアップの保持期間は1〜35日なので、28日は設定できます。

方式復元できる時点代表用途
定期スナップショット取得した各時点日次保全、長期保持、別リージョンコピー
継続バックアップ保持期間内の指定時点誤削除・誤更新前へのPITR

応用編：RDSを28日保護し、別リージョンへ備える

2.1 同じプランに目的別の2ルールを置く

ソースのap-southeast-2では継続バックアップを28日保持し、誤削除前の時刻へPITRできるようにします。災害復旧用には定期スナップショットを作り、コピーアクションで別リージョンのボールトへ複製します。

バックアッププランには複数のルールを置けます。ルールごとにスケジュール、保持期間、ボールト、コピーアクションを分ければ、「細かい時点復旧」と「地域障害への退避」を一元管理できます。

ソースリージョンのPITR

RULE BDaily snapshot

災害復旧の復旧点を作成

COPYDestination vault

別リージョンへ自動複製

2.2 コピー先の復旧点はPITRではない

継続バックアップをリージョン間またはアカウント間でコピーすると、コピー先にはコピー時点のスナップショット型復旧ポイントが作られます。継続バックアップのログ履歴がそのまま移るわけではないため、コピー先で任意時刻のPITRはできません。

したがってRPOは別々に考えます。ソース側の誤操作RPOは継続バックアップ、リージョン障害時のRPOは定期スナップショットとコピー頻度で決まります。

試験対策：「AWS Backup＋クロスリージョンコピー」は正解の方向ですが、「コピー先でも28日間のPITRができる」と読み替えないこと。DR側はコピー済み復旧ポイントの時刻へ戻します。

実務編：権限、暗号化、改ざん耐性、復元訓練

3.1 タグ、IAMロール、KMS

対象はリソースIDで明示するか、タグで動的に選択します。タグ方式なら新しいEC2やEFSを同じ保護方針へ追加しやすい一方、タグ漏れをAWS Configなどで検出する統制が必要です。

AWS Backupはサービスロールの権限で各リソースを操作します。最小権限、バックアップボールトのアクセスポリシー、KMSキーの利用権限を合わせて設計します。クロスアカウントやクロスリージョンでは、コピー先ボールトと暗号化キーの権限も確認します。

Q8. 複数サービスへ安全に拡張する設計として適切なものを2つ選んでください。

3.2 Backup Vault LockとWORM

Backup Vault LockはバックアップボールトへWORM（Write Once Read Many）制御を適用し、保持期間中の削除や保持期間の短縮を防ぎます。ガバナンスモードは適切な権限で変更できます。コンプライアンスモードは猶予期間を過ぎると、顧客のrootを含めてロックを変更・削除できません。

ランサムウェアや内部不正への耐性を高めますが、誤った最小・最大保持期間を固定すると修正できず、保存コストも継続します。別ボールトで検証し、変更可能な猶予期間を設けてから本番化します。

3.3 バックアップ成功ではなく、復旧成功を測る

バックアップジョブの成功だけでは、アプリケーションが復旧できる保証になりません。定期的に隔離環境へ復元し、DBの整合性、接続、アプリ動作、DNSやシークレットの切替手順を確認します。AWS Backupの復元テスト機能に対応するリソースでは、スケジュール化も検討します。

RPOは「どこまでのデータ損失を許容するか」、RTOは「いつまでに業務を再開するか」です。スナップショット頻度はRPOへ、復元・検証・切替にかかる時間はRTOへ反映します。

RESTORE隔離環境へ復元

本番を上書きしない

VALIDATE整合性とアプリを検証

SQL、接続、権限を確認

MEASURERTO・RPOを更新

実測値を手順と監視へ反映

4

総合演習：RDS PostgreSQLの保護設計

ap-southeast-2のRDS PostgreSQLは、自動バックアップ5日、リードレプリカなし、手動スナップショットなしです。要件は、別リージョンへの復旧、28日保持、誤削除からの迅速な復旧、将来のEC2・EFSを含む一元管理です。

4つすべてを満たす軸はAWS Backupです。継続バックアップでソース側PITRを28日保持し、定期スナップショットのコピーアクションで別リージョンへDR用復旧点を作ります。

Q10. すべての要件を満たす最も適切な方針は？

覚え方：「戻す時刻」はPITR。「地域障害」はコピー。「サービス横断」はAWS Backup。「削除させない」はVault Lock。「本当に戻るか」は復元テストです。
