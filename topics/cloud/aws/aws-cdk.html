基礎編：プログラムからCloudFormationを生成する

1.1 AWS CDKはIaC開発フレームワーク

AWS Cloud Development Kit（AWS CDK）は、TypeScript、Python、Java、C#、Goなどの汎用言語でAWSインフラを定義するオープンソースフレームワークです。条件分岐、ループ、型、クラス、テストといったソフトウェア開発の技法を利用できます。

CDKコードを直接AWS APIの命令列として実行するのではありません。cdk synthでCloudFormationテンプレートとアセットを含むクラウドアセンブリへ変換し、CloudFormationがリソースを予測可能に作成・更新・ロールバックします。

1.2 Constructで再利用し、Stackでデプロイする

Constructはリソースを表現する再利用可能な部品です。L1はCloudFormationリソースとほぼ1対1、L2は安全で便利な既定値を持つ高水準API、L3は複数サービスを組み合わせたパターンです。独自Constructには、組織標準の暗号化、タグ、ログ、監視を封じ込められます。

StackはCloudFormationスタックに対応するデプロイ単位です。再利用する論理部品はConstructにし、環境や配備単位の組み立てをStackで行うのが基本です。Stageは複数Stackを開発・検証・本番などのまとまりとしてパイプラインへ追加するときに使います。

概念役割例
Construct再利用・合成する論理部品社内標準VPC、監査付きS3
StackCloudFormationのデプロイ単位NetworkStack、AppStack
Stage環境として複数StackをまとめるDev、Staging、Prod
AppConstructツリー全体のルートプラットフォーム全体

1.3 synth・diff・deployを分ける

cdk synthはコードを実行してテンプレートを生成し、型・構文・合成エラーを検出します。cdk diffはローカル定義とデプロイ済みStackを比較し、追加・削除・変更やIAM権限の差分を表示します。現在のCLIでは読み取り専用変更セットを使い、置換を含む正確な差分を確認できます。

cdk deployは合成結果をCloudFormation経由で適用します。本番レビューでは、Git差分だけでなく、合成テンプレートや cdk diff、CloudFormation変更セットの結果も確認します。

npm test
npx cdk synth ProdStack
npx cdk diff ProdStack
# 承認後にパイプラインが deploy

応用編：複数アカウント・複数環境を一つの設計で展開する

2.1 Environmentと設定オブジェクト

Stackの env にAWSアカウントIDとリージョンを指定すると、配備先が明確になります。同じConstructへ環境別の型付き設定を渡し、開発では小さなインスタンス、本番ではMulti-AZや厳しい保持設定を選ぶ構成にします。

Contextはアプリ、Stack、Constructに関連付けるキー・値です。CLIの --context や cdk.jsonから与えられます。CDKがAWS参照結果をキャッシュする cdk.context.jsonも含め、再現性のためリポジトリへコミットします。ただし秘密情報はContextやGitへ置かず、Secrets Managerなどを参照します。

const configs = {
  dev:  { account: '111111111111', region: 'ap-northeast-1', multiAz: false },
  prod: { account: '222222222222', region: 'ap-northeast-1', multiAz: true }
};

new PlatformStage(app, 'Prod', {
  env: { account: configs.prod.account, region: configs.prod.region },
  config: configs.prod
});

2.2 各アカウント・リージョンをBootstrapする

CDKでデプロイするAWS環境は事前にBootstrapします。Bootstrap Stackは、アセット用S3バケット、ECR、デプロイロールなど、CDKがデプロイに利用する基盤を作ります。対象となるアカウントとリージョンの組み合わせごとに必要です。

クロスアカウントのCDK Pipelinesでは、中央ツールアカウントのパイプラインが対象環境のデプロイロールを引き受けられるよう、信頼関係を含めてBootstrapします。開発端末の長期アクセスキーではなく、IAM Identity CenterやCI用ロールなど短期認証情報を利用します。

cdk bootstrap aws://111111111111/ap-northeast-1
cdk bootstrap aws://222222222222/ap-northeast-1 \
  --trust 999999999999 \
  --cloudformation-execution-policies arn:aws:iam::aws:policy/AdministratorAccess
例をそのまま本番利用しない：上の管理ポリシーは説明用です。実運用では、パイプラインが必要とするCloudFormation実行権限を組織のリスク基準に合わせて制限します。

2.3 ドリフトと手動変更を統制する

Gitにコードを置いても、コンソールから直接変更できる権限が残っていれば、実環境とコードは再び食い違います。通常変更はマージリクエストとパイプラインだけに限定し、緊急変更は期限付き権限と事後コード反映を必須にします。

「誰が何を変えたか」は、Gitコミットとレビューだけでなく、CodePipeline実行履歴、CloudFormation Stackイベント、CloudTrailを関連付けます。CloudFormationのドリフト検出やAWS Configも利用し、コード外の変更を検出します。

問い主な証跡・制御
誰がコードを変えたかGit commit、Merge Request、CODEOWNERS
誰が承認したかGitLab承認、ManualApprovalStep、CodePipeline履歴
AWSで何が変わったかCloudFormationイベント、CloudTrail
コード外の変更はないかドリフト検出、AWS Config、権限制御

実務編：GitLabとCDK Pipelinesで変更を昇格する

3.1 GitLabからCodeConnectionsで取り込む

CDK Pipelinesの CodePipelineエンジンを使う場合、GitLab.comまたはGitLab Self-ManagedをAWS CodeConnectionsでCodePipelineのソースアクションへ接続できます。GitLab Self-Managedではホストリソースも必要です。利用可能リージョンと接続権限を事前確認します。

マージリクエストではlint、単体テスト、CDK assertions、cdk synth、ポリシー検査、cdk diffを実行します。mainへのマージ後にDevへ自動デプロイし、検証後にStaging、承認後にProdへ昇格させます。

3.2 本番前に自動検証と手動承認を置く

CDK PipelinesはStageの前後へShellStepやManualApprovalStepを追加できます。Stagingデプロイ後に疎通・統合テストを行い、Prod Stageの前に承認を置けば、検証結果と変更内容を確認してから本番へ進めます。

さらに ConfirmPermissionsBroadeningを使うと、IAM権限やセキュリティグループ規則が広がる変更だけを人へ回すゲートを構成できます。承認URL、コメント、SNS通知も設定できます。

pipeline.addStage(staging, {
  post: [new pipelines.ShellStep('SmokeTest', { commands: ['npm run smoke'] })]
});

pipeline.addStage(prod, {
  pre: [new pipelines.ManualApprovalStep('ApproveProduction')]
});

Q10. 要件に最も適合するソリューションは？

覚え方：「部品」はConstruct。「配備単位」はStack。「環境のまとまり」はStage。「生成」はsynth。「事前差分」はdiff。「AWSへの適用」はCloudFormation。「昇格と承認」はPipelineです。
