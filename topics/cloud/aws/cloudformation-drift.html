AWS CloudFormation
テンプレート設計とドリフト検出

テンプレートを正本（Source of Truth）として、コンソールやAPIから加えられた管理外変更を検出します。IAMカスタマー管理ポリシーを例に、定期検出、非同期処理、通知、原因追跡まで整理します。

今回の設問の結論

EventBridgeでLambdaを定期起動し、CloudFormationのドリフト検出結果がDRIFTEDならSNSで通知します。

CloudFormationテンプレートが期待構成をすでに保持しているため、比較用JSONをS3へ二重管理する必要がありません。カスタマー管理ポリシーを AWS::IAM::ManagedPolicy として定義していれば、現在のCloudFormationドリフト検出対象です。

現在の実装：定期実行には、旧来のEventBridgeスケジュールルールよりEventBridge Schedulerが推奨です。またCloudFormationは検出完了時にEventBridgeへ状態変更イベントを発行するため、Lambdaを数分待機させず、完了イベントをSNSへ送る構成も選べます。

出典：CloudFormationドリフト検出、ドリフト状態変更イベント

基礎編：ドリフトは「正本との差分」

1.1 テンプレートと実リソースを比較する

CloudFormationのドリフト（drift）は、テンプレートとパラメータから決まる期待構成と、現在のAWSリソースの構成が食い違った状態です。コンソール、CLI、SDKからスタック外でプロパティを変更した場合や、管理対象リソースを削除した場合に発生します。

スタック内の対応リソースが1つでも変更されると、スタックのドリフト状態は DRIFTED になります。すべて一致すれば IN_SYNC、未確認は NOT_CHECKED です。

EXPECTEDTemplate＋Parameters

期待するIAMポリシー

COMPAREDrift detection

対応プロパティを比較

ACTUALAWS resource

現在の実構成

Q1. CloudFormationのドリフトとは？

1.2 比較されるのは明示プロパティと対応リソースだけ

CloudFormationは、テンプレートまたはパラメータで明示したプロパティだけをドリフト比較します。既定値も監視したい場合は、既定値と同じ値であってもテンプレートへ明示します。

リソースタイプごとに対応状況が異なります。現在、AWS::IAM::ManagedPolicy、AWS::IAM::Role、AWS::IAM::RolePolicyなどは対応しています。一方、複合リソースのAWS::IAM::Policyは公式の対応一覧に掲載されていないため、同じ「IAMポリシー」でも型を確認します。

確認点今回
リソースタイプAWS::IAM::ManagedPolicy
期待値テンプレートのPolicyDocument等
実際値IAMに現在適用されているポリシー
差分リソースはMODIFIED、スタックはDRIFTED

応用編：非同期APIと状態コード

2.1 DetectStackDriftは結果をすぐ返さない

DetectStackDriftは検出処理を開始し、StackDriftDetectionIdを返します。処理は数分かかる場合があるため、そのIDを使ってDescribeStackDriftDetectionStatusを確認します。完了後に詳細が必要ならDescribeStackResourceDriftsを呼びます。

同じスタックで同時に実行できるドリフト検出は1つです。Lambdaでポーリングする場合は、タイムアウト、バックオフ、重複起動、DETECTION_FAILEDも処理します。

  1. DetectStackDrift

    検出を開始し、検出IDを受け取ります。

  2. DescribeStackDriftDetectionStatus

    DETECTION_IN_PROGRESSから完了または失敗まで確認します。

  3. StackDriftStatusを判定

    DRIFTEDなら通知し、必要に応じてリソース差分を取得します。

出典：DetectStackDrift API

Q3. ドリフト検出の正しい順序へ並べ替えてください。

  • DescribeStackResourceDriftsで詳細を取得
  • DetectStackDriftで開始
  • DescribeStackDriftDetectionStatusで完了確認

2.2 「処理状態」と「差分状態」を分ける

種類主な値意味
DetectionStatusDETECTION_IN_PROGRESS / DETECTION_COMPLETE / DETECTION_FAILED比較処理そのものの進捗
StackDriftStatusDRIFTED / IN_SYNC / NOT_CHECKED期待構成との差分
ResourceDriftStatusMODIFIED / DELETED / IN_SYNC個別リソースの差分
失敗を正常扱いしない：DETECTION_FAILEDでは一部結果が得られる場合がありますが、監視としてはエラー通知し、権限不足やAPIエラーを調査します。

EventBridge SchedulerからLambdaを定期起動し、対象スタックのドリフト検出を開始します。Lambdaが完了まで確認し、StackDriftStatus=DRIFTEDなら、スタックARN、アカウント、リージョン、ドリフトしたリソースをSNSへ発行します。

これは提示された4選択肢では最も管理作業が少ない解答です。期待値をCloudFormationテンプレートに一本化でき、独自のJSON比較ロジックやS3上の第二の正本を持たずに済みます。

Q5. 設問の要件を最小管理で満たす構成は？

3.2 完了イベントならLambdaを待機させずに済む

CloudFormationは、検出の開始・完了・失敗を「CloudFormation Drift Detection Status Change」イベントとしてEventBridgeへ送ります。開始用LambdaはDetectStackDriftを呼んだら終了し、別ルールでDETECTION_COMPLETEかつDRIFTEDを絞り込んでSNSへ送れます。

このイベント駆動構成は、Lambda内で数分ポーリングするより実行時間とタイムアウト管理を減らせます。設問の正解の意図を保ちながら、実装をより疎結合にできます。

{
  "source": ["aws.cloudformation"],
  "detail-type": ["CloudFormation Drift Detection Status Change"],
  "detail": { "status-details": {
    "detection-status": ["DETECTION_COMPLETE"],
    "stack-drift-status": ["DRIFTED"]
  }}
}

出典：Drift Detection Status Change event

実務編：証跡・権限・複数アカウント

4.1 CloudTrailは「誰が変えたか」、ドリフトは「何が違うか」

サービス答える問い今回の役割
CloudFormation drift正本と今の構成は違うか差分検出
CloudTrail誰が、いつ、どのAPIを呼んだか原因・操作主体の追跡
IAM Access Analyzer外部アクセスや実利用権限をどう絞るか最小権限の検討
Trusted Advisor既知のベストプラクティスに違反していないか広い運用チェック

CloudTrailだけでもCreatePolicyVersionやSetDefaultPolicyVersionなどの変更APIを追跡できますが、変更パターンの列挙やテンプレートとの差の判断が別途必要です。ドリフト通知で対象を特定し、CloudTrailで変更者と時刻を調べる組み合わせが明快です。

Access Analyzerのポリシー生成は、CloudTrailアクティビティを基に実際に使った権限の案を作る機能です。デプロイした期待ポリシーの同一性を確認する機能ではありません。

Q7. ドリフト通知後に「誰が変更したか」を調べるサービスは？

4.2 複数アカウント運用のチェックリスト

  1. 対象型を確認

    AWS::IAM::ManagedPolicyなど、公式一覧で対応を確認します。

  2. 監視したい値を明示

    既定値任せにせず、重要プロパティをテンプレートへ明記します。

  3. 検出権限を最小化

    cloudformation:DetectStackDrift等と、対象リソースの読取権限だけを付与します。

  4. 各アカウントへ同じ監視を展開

    StackSetsまたはパイプラインでScheduler、Lambda、SNS連携を標準化します。

  5. 通知を運用可能にする

    アカウント、リージョン、スタック、論理ID、差分を含めます。

  6. 復旧方針を決める

    テンプレートへ戻すか、正当な緊急変更をコードへ取り込むかをレビューします。

自動修復は慎重に：検出直後にスタック更新で上書きすると、障害対応中の緊急変更を消す可能性があります。最初は通知と承認を挟み、変更権限もパイプライン中心へ絞ります。
AWS Configのマネージドルールを使う選択肢
CLOUDFORMATION_STACK_DRIFT_DETECTION_CHECKを使うと、Configがスタックのドリフトを評価できます。多くのスタックを継続的なコンプライアンスとして扱う場合は、Lambdaコードを減らせる実務上の候補です。ただし今回の4択には含まれず、通知まで含む設計や評価頻度・費用は別途決めます。

出典：AWS Config managed rule

総合演習：IAMポリシーの変更を検出する

4つの選択肢を比較する

方式判定理由
定期ドリフト検出＋SNS正解テンプレートを正本として再利用できる
Trusted Advisor不正解個別ポリシーのデプロイ後差分を検出しない
Access Analyzer生成結果との比較不正解実利用権限の案であり期待ポリシーではない
S3上のJSONと独自比較不正解正本の二重管理と独自処理が増える
CloudTrailが設定済みである意味：ドリフト検出の実行にCloudTrailは必須ではありません。通知後に変更者・API・時刻を追跡できる監査証跡として利用します。

覚えておく3行

追加演習：再利用・ダッシュボード・失敗調査

既存ダッシュボードをスタックごとに再現する

CloudWatchコンソールのView/edit source、またはGetDashboardでJSONを取得し、AWS::CloudWatch::Dashboardの必須DashboardBodyへ組み込みます。DashboardNameは省略するか!Sub '${AWS::StackName}-ops'のように一意化します。ダッシュボードはアカウント内でグローバルで、同名固定は複数スタックで衝突します。

Refの意味：同じテンプレートのDashboardリソースに対するRefはDashboardNameを返します。既存ダッシュボードのARNから内容を複製する機能ではありません。

単一テンプレートを開発・検証・本番で再利用する

環境ごとに変わるインスタンスタイプ、VPC ID、容量などをParametersへ外出しし、必要に応じてMappingsとConditionsを組み合わせます。User dataはEC2の初期化、Nested Stackは構造分割、Stack Policyは更新保護であり、環境値の注入そのものではありません。

読み取り専用属性をPropertiesへ書かない

AWS::EC2::InstanceのPublicDnsNameは作成後にFn::GetAttで読む属性であり、設定可能なプロパティではありません。テンプレート内に書くと検証エラーになります。設問のAMI IDやSubnet IDが例示用プレースホルダーなら、実環境では有効な値へ置換します。

作成失敗後も成功済みリソースを残す

create-stack --on-failure DO_NOTHING、または--disable-rollbackを使います（同時指定不可）。スタックはCREATE_FAILEDとなり、成功済みリソースを観察して修正後に再試行できます。ROLLBACKは既定動作で削除され、RollbackConfigurationはCloudWatchアラームのトリガー設定です。
