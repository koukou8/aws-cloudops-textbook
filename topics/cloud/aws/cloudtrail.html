基礎編

基礎

1.1 CloudTrailは、AWS操作の記録係

AWS CloudTrailは、ユーザー、IAMロール、AWSサービスが行った操作をイベントとして記録するサービスです。コンソール、AWS CLI、SDKなどを通した操作を追い、監査や障害調査に使います。

たとえば「EC2が停止した」という事象に対し、StopInstancesを実行したロール、時刻、対象インスタンス、リクエスト元などを調べられます。操作の記録であり、EC2内で実行したシェルコマンドやアプリの全処理が自動的に記録されるわけではありません。

調べたいこと主な確認先例
誰がAWSを操作したかCloudTrailEC2停止、IAM権限変更、S3オブジェクト取得
どのようにシステムが動いたかCloudWatchのメトリクス・ログ等CPU使用率、アプリエラー、レイテンシー
どの通信が観測されたかVPCフローログ送信元・宛先IP、ポート、ACCEPT／REJECT

1.2 管理イベントとデータイベント

CloudTrailで何が記録されるかは、イベントの種類と設定によります。「CloudTrailがあるから全操作が記録される」とは判断せず、必要な操作を収集対象に含めます。

種類主な対象設定の考え方
管理イベントリソースの作成・設定変更・削除など。例：StopInstances、CreateRoleコントロールプレーンの操作。証跡の基本的な記録対象
データイベントリソースのデータに対する操作。例：S3 GetObject、Lambda Invoke必要なリソースや操作を明示して選ぶ。通常は既定で記録されない
ネットワークアクティビティイベント対応サービスのVPCエンドポイント経由のAWS APIアクセス追加設定が必要。VPCフローログの通信記録とは対象が異なる
Insightsイベント対応するAPI呼び出し量やエラー率の異常な変化追加の分析機能。必要に応じて有効化する
医療データの監査なら：バケットの設定変更だけでなく、オブジェクトの取得や削除を追いたい場合は、S3の該当データイベントも対象にします。ログには操作の情報が記録され、オブジェクト本文が丸ごと保存されるわけではありません。

1.3 JSONログを読む

次はEC2の停止要求を表す学習用の抜粋です。ロールを引き受けたセッションによる操作を想定しています。

{
  "Records": [{
    "eventTime": "2026-10-28T23:00:00Z",
    "eventSource": "ec2.amazonaws.com",
    "eventName": "StopInstances",
    "awsRegion": "ap-northeast-1",
    "userIdentity": {
      "type": "AssumedRole",
      "arn": "arn:aws:sts::111122223333:assumed-role/Operations/operator-session"
    },
    "sourceIPAddress": "192.0.2.10",
    "requestParameters": {
      "instancesSet": {
        "items": [{"instanceId": "i-0123456789abcdef0"}]
      }
    }
  }]
}
項目読むポイント
eventTime操作が発生した時刻。ZはUTCで、例は日本時間10月29日8:00
eventSource / eventNameどのサービスの、どの操作か
userIdentityIAMユーザー・ロール・セッション等の実行主体
sourceIPAddress / userAgent要求元やクライアントの手掛かり。これだけで人を断定しない
requestParameters / errorCode要求した対象・条件と、失敗があった場合の情報
操作要求の記録だけで、アプリやリソースの最終状態まで保証されるわけではありません。非同期処理なら、対象リソースの状態も合わせて確認します。また、ログ内の並びがイベント発生順とは限りません。

応用

2.1 イベント履歴と「証跡」は別のもの

仕組み何ができるか今回の要件との関係
イベント履歴各リージョンの過去90日分の管理イベントを検索・表示する。アカウントで自動的に利用可能最近の操作の調査向け。データイベントは表示されない
証跡（Trail）対象イベントと配信先を設定し、ログを継続的にS3へ配信する長期保存や、S3ログの整合性検証に使う
組織の証跡AWS Organizationsの複数アカウントをまとめて記録する全社の監査ログを中央へ集約する構成に使う

証跡はログファイルそのものではなく、収集と配信の設定です。マルチリージョン証跡では、適用範囲のリージョンからログを収集できます。記録するイベント、収集範囲、S3保存期間はそれぞれ設計します。

S3に置いた証跡ログは、Athenaなどで分析できます。必要ならCloudWatch Logsへも配信して監視へつなげます。今回の署名付きダイジェストによる検証は、証跡から配信されるS3ログが対象です。

CloudTrail Lakeはどう位置付ける？
CloudTrail Lakeは監査イベントを保存・SQL分析する機能ですが、2026年5月31日から新規顧客の受付が終了しています。既存顧客は継続利用できます。CloudTrailの証跡自体は引き続き提供されています。新規設計ではS3＋AthenaやCloudWatchなど、現在利用できる分析方法を検討します。

Q4. S3へ長期保存し、配信後のログ改変を検証したい場合は？

2.2 ハッシュ＋電子署名＋ダイジェストの連鎖

ハッシュは、ファイルの内容から計算する固定長の値です。内容が変わると値も変わります。ただし、ログと比較用ハッシュ値の両方を書き換えられたら、値を比べるだけでは元のログであると確認できません。

CloudTrailの整合性検証では、ログごとにSHA-256ハッシュを計算します。さらに1時間ごとに、その時間帯に配信したログの参照先とハッシュなどをまとめたダイジェストファイルを配信します。ダイジェストにCloudTrailの秘密鍵で署名することで、比較の基準自体の書き換えも検知します。

01 ログを要約SHA-256ハッシュ

ログの内容を値に変換し、ダイジェストへ記録

02 比較の基準を保護電子署名

CloudTrailの秘密鍵で署名し、対応する公開鍵で確認

03 後から照合署名とログを検証

ダイジェストを検証し、ログのハッシュを再計算して比較

ログとダイジェストは同じ証跡用S3バケットの別プレフィックスに保存されます。ダイジェストは前のダイジェストのハッシュ・署名情報も参照し、連鎖を作ります。現在のダイジェストの署名は、そのS3オブジェクトのメタデータに保存されます。

監査では、公開鍵による署名の確認、ログのハッシュ照合、ダイジェスト間の連鎖の確認を組み合わせます。対象となるログの改変や欠落を検知できますが、記録対象に設定していない操作まで復元できる仕組みではありません。

有効化と検証実行は別です。有効化は、ダイジェストを生成・配信するための設定です。自動で継続的に検証結果を通知する設定ではありません。CLI等で検証し、継続確認が必要なら実行と通知を定期化します。

実務

3.1 有効化と検証のCLI

以下は既存の記録中の証跡を使う例です。証跡名・アカウントID・リージョン・時刻は環境に合わせて置換します。証跡の設定変更はホームリージョンで行います。教材はこれらのコマンドを実行しません。

# 1. ダイジェストの生成・配信を有効化（設定変更）
aws cloudtrail update-trail \
  --name audit-trail \
  --enable-log-file-validation \
  --region ap-northeast-1

# 2. 設定と配信状況を確認（参照操作）
aws cloudtrail get-trail \
  --name audit-trail --region ap-northeast-1

aws cloudtrail get-trail-status \
  --name audit-trail --region ap-northeast-1

# 3. 対象期間を検証（参照操作）
aws cloudtrail validate-logs \
  --trail-arn arn:aws:cloudtrail:ap-northeast-1:111122223333:trail/audit-trail \
  --start-time 2026-10-27T00:00:00Z \
  --end-time 2026-10-28T00:00:00Z \
  --region ap-northeast-1 \
  --verbose

get-trailでは LogFileValidationEnabled、get-trail-statusでは記録状態やダイジェスト配信エラーなどを確認します。有効化後、ダイジェスト配信が始まるまでおよそ1時間かかります。検証期間は、実際にダイジェストが生成された期間に合わせます。

validate-logsはS3上のログとダイジェストを取得して検証します。対象S3への読み取り、バケットの所在確認、必要なCloudTrail操作などの権限が必要です。SSE-KMSで暗号化している場合は、対象キーによる復号権限も確認します。

標準CLIの前提：ログとダイジェストをCloudTrailが配信した元のS3の場所で利用します。ローカルへダウンロードしたファイルだけを渡す検証コマンドではありません。移動済みログには別途カスタム検証が必要になります。

3.2 継続的な検証と結果の読み方

画像の要件を継続運用へ落とし込むなら、標準の整合性検証を有効にしたうえで、CLIを実行するジョブを定期化します。たとえばEventBridge SchedulerでSSM Automation等を起動し、CLIを実行する環境へつなぎます。検証結果の保存と、失敗・未実行時の通知を設定します。

「検証に成功したもの」だけでなく、想定期間のダイジェストが揃っているか、検証対象が0件になっていないかも確認します。エラー時は、改ざんだけでなくS3権限、KMS権限、配信障害、リージョンや対象時刻の指定を調べます。

結果・状況意味と次の確認
Log file: valid参照元ダイジェストを含め検証でき、配信後にログ内容が変わっていない
hash value doesn't matchログ内容のハッシュが記録値と一致しない
signature verification failedダイジェストの署名が有効ではなく、参照するログへの信頼を確立できない
not found／取得エラー欠落・削除、場所の指定、アクセス権などを調査する
ダイジェストが不足機能の無効化、記録停止、配信遅延・障害などを確認する
過去へさかのぼって生成されません。整合性検証が無効だった間に配信されたログのダイジェストは、後から有効化しても作成されません。機能の無効化や記録停止で連鎖が切れることもあります。定期確認では配信エラーや欠損期間も記録します。

Q8. 昨日まで整合性検証が無効で、今日有効にしました。昨日配信されたログは？

3.3 検知・削除防止・暗号化を組み合わせる

目的主な仕組み役割
配信後の変更を検知CloudTrailの整合性検証署名とハッシュを照合する
削除・上書きを制限S3 Object Lock、IAM・バケットポリシー保持期間や権限により保存したオブジェクトバージョンを保護する
過去版を保持S3バージョニング履歴の保存・復旧に使う。権限次第では過去版も削除可能
内容の機密性を保護S3のサーバー側暗号化、KMS等保存内容を暗号化し、読み取りを制御する

組織の証跡を監査用アカウントのS3へ集約し、書き込み・削除・検証の権限を分離する構成も使われます。監査側が必要なログとダイジェストを読み取れるようにし、記録停止や証跡設定の変更も監視します。

Object LockはS3のオブジェクトバージョンを保護する機能です。署名付きダイジェストによる検証と役割が異なります。暗号化も、CloudTrailの配信元とログ内容の整合性を確認する処理の代わりにはなりません。

出典：S3 Object Lock、組織の証跡

総合演習：画像の設問を解く

ログの真正性を、少ない運用負担で検証したい

求められているのは、作成・配信されたログが後から変わっていないかを確かめる手段です。既存のCloudTrail標準機能を使う3番目が、最も直接的に要件を満たします。

選択肢判断理由
1. Lambdaでハッシュを計算しS3タグへ保存最適ではないタグ自体の変更対策、検証処理、例外対応などを自作する必要がある
2. Lambdaでハッシュを計算しParameter Storeへ保存最適ではない標準機能で可能なことに、別の保存先・権限・実装の運用が増える
3. 証跡でログファイルの整合性検証を有効化正解CloudTrailが署名付きダイジェストを生成し、標準CLI等で照合できる
4. S3側でCloudTrail専用の検証機能を有効化誤り設定するのはCloudTrailの証跡。S3チェックサムやObject Lockとは異なる
「継続的に確認」の実装：選択肢3で検証の基盤を整え、必要な頻度で検証ジョブを実行します。監査チームは必要時にも同じ仕組みで検証できます。設定だけで検証が毎回自動実行される、という意味ではありません。

S3アクセス調査とCloudTrail Insights

大量のLISTリクエストの送信元を調べる

S3サーバーアクセスログは送信元IP、リクエスタ、操作、HTTP状態などを記録します。CloudTrailではListObjects／ListObjectVersionsなどをS3オブジェクトのデータイベントとして記録でき、IAMプリンシパルやUser-Agentを追跡できます。データイベントは既定で無効かつ有料なので、事前に有効化した範囲だけを遡れます。

出典：S3のCloudTrailイベント

API活動の統計的な逸脱を検出する

CloudTrail Insightsは管理イベントの書き込みAPIコール率と、読み書きAPIのエラー率について通常パターンを学習し、逸脱をInsightsイベントとして記録します。GuardDutyの脅威検出、Inspectorの脆弱性評価、Configの構成準拠とは目的が異なります。EventBridgeで通知や自動対応へつなげます。
