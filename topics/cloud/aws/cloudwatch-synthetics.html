今回の結論

CloudWatch SyntheticsでCanaryを作成し、主要ページ・リンク・期待コンテンツを定期テストします。失敗時はCloudWatchアラームから通知します。

404にはBroken Link Checker、終了済みキャンペーンの残存には文言のアサーションまたはVisual Monitoringを使います。インフラメトリクスが正常でも、ユーザー体験の異常を独立して検知できます。

  • 認証、VPC、複数ロケーション、ランタイム更新を本番運用へ落とし込む。

基礎

1.1 Canaryは利用者の行動を先回りして再現する

CloudWatch SyntheticsのCanaryは、設定したスケジュールでエンドポイントやAPIへアクセスするスクリプトです。実際のトラフィックがない時間でもページを開き、リンクをたどり、フォームやログインフローを操作できます。

CanaryはNode.js、Python、Javaで記述でき、ヘッドレスブラウザーにはPuppeteer、Playwright、Seleniumを利用できます。選べる言語・フレームワークはランタイムごとに異なるため、目的に合う最新のサポート対象ランタイムを選びます。

Broken Link Checkerは指定ページ内のリンクを収集し、指定した上限まで検査します。404だけでなく、不正なURL、空応答、タイムアウトなども検出できます。ランタイムによって利用できるBlueprintが異なり、Broken Link CheckerはPlaywrightランタイムではサポートされません。

「古いキャンペーンが表示されている」はHTTP 200でも発生します。期待する新しい文言の存在、終了済み文言の非存在、DOM要素やリンク先を明示的にアサートします。Visual Monitoringは補助になりますが、時刻・広告・利用者名など動的領域を除外しないと誤検知が増えます。

2.2 重要導線を短いStepへ分ける

1つの巨大なスクリプトで全ページを巡回するより、トップ表示、商品検索、詳細表示、ログインなど、利用者にとって意味のあるStepへ分けます。executeStep()やexecuteHttpStep()を使うと、StepName単位のSuccessPercentとDurationも発行できます。

監視頻度は障害の検知目標と費用で決めます。Canaryは1回実行またはrate／cronでスケジュールでき、rateは最短1分です。すべてを1分間隔にせず、最重要導線と低頻度ページで頻度を分けます。

実務編：メトリクス・アラーム・原因調査

実務

3.1 SuccessPercentを通知へつなぐ

CanaryはCloudWatchSynthetics名前空間へSuccessPercent、Duration、2xx、4xx、5xx、Failed requestsなどを発行します。基本の可用性アラームはSuccessPercentを使い、連続失敗数、評価期間、欠損データの扱いを監視間隔に合わせます。

1回の失敗ですぐ通知すると、一時的な名前解決や外部依存の揺らぎでノイズが増える場合があります。一方、重大な購入導線は単発失敗でも通知するなど、業務影響で閾値を分けます。通知先にはAmazon SNSやインシデント管理連携を設定します。

メトリクス見えること代表的な使い方
SuccessPercent実行が成功し、失敗を検出しなかった割合可用性アラーム
DurationCanary全体またはStepの所要時間体感性能の劣化
4xx / 5xxブラウザー・APIが受けたHTTPエラー数リンク・サーバー異常の補助指標
VisualMonitoringSuccessPercent基準画像と一致した割合画面差分の監視

出典：AWS公式：Canary metrics

Q6. Canaryの失敗をCloudWatchアラームへつなぐ基本メトリクスは？

3.2 失敗時は成果物を時系列で読む

  1. 失敗Stepと時刻を確認

    SuccessPercent、Duration、4xx／5xx、StepNameを見ます。

  2. スクリーンショットを確認

    利用者が見た画面、クリック対象、表示崩れを確認します。

  3. HARとログを確認

    失敗したHTTP要求、リダイレクト、DNS・TLS・タイムアウトを切り分けます。

  4. アプリ内部へ進む

    X-Ray、アプリログ、依存サービスのメトリクスと同じ時刻を照合します。

  5. 誤検知ならテストを修正

    動的領域、セレクター、タイムアウト、期待値、再試行を見直します。

成果物もデータです。スクリーンショット、HAR、レポートはS3へ保存されます。認証Cookie、URLパラメータ、PIIが含まれる可能性を評価し、暗号化、アクセス権、保持期間、ログのマスキングを設計します。

実務編：安全で保守できるCanary

実務

4.1 マネージドでも運用設計は残る

コンソールからCanaryを作成すると、実行用Lambda、Lambda Layer、IAMロール、CloudWatch Logs、成果物用S3バケット、任意のアラームなどが作成されます。Syntheticsはこの統合を管理しやすくしますが、権限・費用・ランタイム・保持を無視できるわけではありません。

実行ロールは対象URL、CloudWatch、S3、必要なSecrets Managerなどへ最小権限にします。ログイン資格情報をコードへ直書きせず、監視専用ユーザーを使い、実データの更新や注文確定を起こさない安全なテスト経路を用意します。

公開サイト

通常のCanaryから外部URLへアクセス。WAFやbot制御で監視を誤遮断しないか確認。

VPC内サイト

CanaryをVPCへ関連付け、サブネット、Security Group、DNS、S3・CloudWatchへの送信経路を設計。

出典：AWS公式：Creating a canary、AWS公式：Artifact encryption

Q8. 認証後ページを監視する安全な方法は？

4.2 ランタイムと監視コードも変更管理する

Syntheticsのランタイムにはサポート期限があります。最新ランタイムを検証して更新し、DOMセレクターや期待文言をアプリ変更と同じリポジトリ・レビュー・パイプラインで管理します。Safe canary updatesのDry Runを使えるランタイムでは、本番スケジュールへ確定する前に変更を検証できます。

複数地域からの体験差を調べる場合はMultilocation Canaryを検討します。LocationディメンションのSuccessPercentとDurationで地域別に比較し、集約メトリクスで全体アラームを作れます。監視場所を増やすほど実行回数と費用も増えるため、利用者分布と障害仮説から選びます。

総合演習：404と古いキャンペーンを早期検知

公開サイトの主要ページに404があり、別ページでは終了済みキャンペーンが表示されています。バックエンドとネットワークのメトリクスは正常で、運用負荷を抑えながら利用者より先に検知したい状況です。

Q10. 最も運用オーバーヘッドが小さい解決策は？

最小構成：Broken Link Checker＋重要ページの文言アサーション、5分程度の定期実行、SuccessPercentのアラーム、SNS通知、失敗時のスクリーンショット／HAR確認から始めます。監視対象と頻度は重要度に応じて段階的に増やします。
