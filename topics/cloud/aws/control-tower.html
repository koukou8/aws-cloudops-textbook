基礎編：マルチアカウントの骨格を作る

1.1 OrganizationsとControl Towerの役割

AWS Organizationsは、複数のAWSアカウントを組織へまとめ、組織単位（OU）を階層化し、ポリシーを継承させる土台です。AWS Control TowerはOrganizationsを含む複数サービスをオーケストレーションし、ベストプラクティスに沿うランディングゾーンを構築・運用します。

ランディングゾーンには管理アカウント、ログアーカイブアカウント、監査アカウントなどの共有構成が含まれます。ワークロードは開発・検証・本番などのOUとメンバーアカウントへ分離し、管理アカウントには通常のワークロードを置かない設計が基本です。

1.2 ベースラインとAccount Factory

ベースラインは、対象へ適用するリソースと構成のまとまりです。OUをControl Towerへ登録してAWSControlTowerBaselineを有効化すると、そのOUのメンバーアカウントへコンプライアンス監視、監査、セキュリティ監視などに必要な構成が継承されます。

Account Factoryで新しいアカウントを登録済みOUへ発行すると、そのOUのベースラインとコントロールを継承します。アカウントごとにConfigルールやIAMロールを手作業で配布するより、一貫性と運用効率を高められます。

要素主な役割
ランディングゾーン組織全体の共有アカウント、リージョン、統制の基盤
AWSControlTowerBaselineOU配下のアカウントへ標準リソースと構成を継承
コントロール禁止・検知・デプロイ前検査などの統制をOUへ適用
Account Factory承認済みの設定で新しいメンバーアカウントを発行

Q3. 未承認リージョンへの作成要求を実行前に拒否する統制は？

2.2 統制対象リージョンは許可リストではない

ランディングゾーン設定の「統制対象リージョン」は、Control Towerがベースラインやリージョン対応コントロールを展開・監視する範囲です。リージョンを統制対象から外しても、そのリージョンでリソースを作成できなくなるわけではありません。単にControl Towerのガバナンス外となります。

承認外リージョンへのAPI操作を拒否するには、ランディングゾーン全体のRegion denyコントロール AWS-GR_REGION_DENY を有効化します。OUごとに異なる許可リージョンが必要なら、構成可能なOU単位の CT.MULTISERVICE.PV.1 を検討します。

混同しない：①承認リージョンを統制対象に選ぶ、②Region denyを有効化する、③OUを登録してベースラインを適用する、の3つは別の操作です。リージョン構成変更後、既存アカウントへ反映するためOUの再登録・更新が必要になる場合があります。

2.3 SCPは権限を与えず、上限を決める

Service Control Policy（SCP）は、組織ルート、OU、アカウントへ付ける権限の上限です。SCPで許可しただけでは操作権限は付与されず、IAMポリシーなどのAllowも必要です。一方、適用されるSCPに明示的Denyがあれば、メンバーアカウントのAdministratorAccessやrootユーザーでも実行できません。

リージョン拒否ではグローバル条件キーaws:RequestedRegionを使います。ただしIAM、Organizations、Route 53などのグローバルサービスや、クロスリージョン動作を必要とするAPIには例外設計が必要です。Control Tower管理のSCPを直接編集するとドリフトになるため、管理機能から設定します。

{
  "Effect": "Deny",
  "NotAction": ["iam:*", "organizations:*", "route53:*"],
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": ["ap-northeast-1", "ap-southeast-2"]
    }
  }
}

概念例です。実際はControl TowerのRegion denyコントロールと公式の例外一覧を使用し、影響をテストします。

管理アカウント例外：SCPはメンバーアカウントに適用されますが、Organizationsの管理アカウント内のユーザーとロールには影響しません。管理アカウントをワークロード用途に使わず、アクセスを厳格に管理します。

出典：Service Control Policy、SCP構文とリージョン制限例

3

実務編：安全に展開し、継続運用する

3.1 推奨する導入順序

  1. ワークロード配置方針からホームリージョンと追加の統制対象リージョンを決めます。
  2. ランディングゾーンを構築し、ログアーカイブ・監査アカウントを分離します。
  3. 開発・検証・本番などのOUを登録し、AWSControlTowerBaselineを有効化します。
  4. ランディングゾーン全体またはOU単位でRegion denyを有効化し、許可リージョンと例外を定義します。
  5. サンドボックスOUで拒否動作とグローバルサービスへの影響を検証します。
  6. Account Factoryで新規アカウントを発行し、既存OU・アカウントも必要に応じて再登録・更新します。
  7. ベースラインとコントロールのドリフト、Configの準拠状況、CloudTrail操作を継続監視します。

Q6. Region denyを本番OUへ展開する前に優先することは？

3.2 独自実装を増やさない

全アカウントへLambdaを配布して未承認リージョンのリソースを削除する設計は、検知の遅延、削除権限、再試行、例外処理、ログ、コード更新を自社で管理する必要があります。Configルールだけの方式も発見的で、作成前の拒否にはなりません。

共通要件はControl Tower管理のコントロールとベースラインへ寄せます。標準機能で表現できない独自要件だけをカスタムSCPやAccount Factory Customizationなどへ分離し、Control Towerが管理するリソースを直接変更しないことが運用効率につながります。

方式問題点・使いどころ
Configで検知・削除事後対応。準拠状況の可視化には有効
Lambdaで自動削除事後対応に加え、コードと全アカウント展開の保守が必要
ユーザー別IAM権限ユーザー数に比例して管理が増え、別経路のロールを覆えない
Control Tower＋SCPOU単位で予防し、新規アカウントへ継承できる

総合演習：金融サービス企業のリージョン統制

要件は、Control Towerで構築するすべてのメンバーアカウントへ標準ベースラインを適用し、承認外リージョンでの作成を事前に拒否することです。最もマネージドな実装は、承認リージョンをControl Towerの統制対象に設定し、ランディングゾーンのRegion denyを有効化し、登録OUへAWSControlTowerBaselineを適用することです。

提示された選択肢だけで2つ選ぶ試験問題では、「aws:RequestedRegionを使うSCP」と「ランディングゾーンのリージョン設定」が想定解です。ただし、後者だけでは拒否になりません。実装時は別々の独自SCPとControl Tower管理SCPを重ねるのではなく、Control TowerのRegion denyコントロールとして管理するのが基本です。

提示された選択肢判定実務上の補足
各アカウントへConfig＋削除不正解発見的・事後対応で個別管理が増える
各アカウントへLambda＋削除不正解事後対応で、独自コードの保守が必要
aws:RequestedRegionのSCP正解の原理Control Tower管理のRegion denyとして有効化する
統制対象リージョンを更新正解の一部ベースライン展開範囲。拒否にはRegion denyも必要
ユーザー別Identity Center設定不正解組織・OU単位の一貫した権限上限にならない
