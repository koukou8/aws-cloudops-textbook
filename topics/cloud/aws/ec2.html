基礎編：AMIとEBSを分けて理解する

1.1 AMIはEC2を再現する起動テンプレート

Amazon Machine Image（AMI）は、新しいEC2インスタンスを起動するための情報をまとめたイメージです。EBS-backed AMIでは、OSが入ったルートボリュームや追加EBSボリュームのスナップショットと、どのデバイスとして接続するかを示すブロックデバイスマッピングが中心になります。

AMI自体を「サーバーの完全な実行状態」と考えてはいけません。CPUやメモリ上の実行状態を保存するものではなく、再起動可能なディスク内容と起動設定を残します。

1.2 複数EBSボリュームもAMI作成の対象

実行中のEBS-backedインスタンスからAMIを作ると、EC2はルートボリュームと、インスタンスに接続されている追加EBSボリュームのスナップショットを作成します。新しいインスタンスをAMIから起動すると、スナップショットを基にEBSボリュームが作られます。

インスタンスストアは一時ストレージです。ブロックデバイスマッピングに情報を含めることはできますが、元のインスタンスストアのデータはAMIへ保存されません。永続化が必要な注文データはEBSなどへ置きます。

追加EBS接続中の各ボリュームをスナップショット化マッピングに従って新しいEBSを作成
インスタンスストア元データは保存されない空の一時ストレージとして提供

応用編：停止時間と整合性を判断する

2.1 APIパラメーターはNoReboot

CreateImage APIの正式なパラメーターはNoRebootです。falseまたは省略が既定で、AMI作成前にインスタンスを停止・再起動します。これにより、バッファーやメモリ上の書き込み対象をボリュームへ反映してからスナップショットを作れます。

NoReboot=trueなら稼働を続けたまま作成できますが、スナップショットに入るのはその時点までにボリュームへ書かれたデータです。AWSは、この方法で作成したイメージのファイルシステム整合性を保証しません。

CreateImageの指定インスタンス整合性向く場面
NoReboot=false／省略停止してスナップショット後に再起動ファイルシステムの整合性を確保短い停止を許容でき、整合性を優先
NoReboot=true稼働したままクラッシュ整合性。未書き込みデータは含まれないアプリ側で事前に静止できる場合など

2.2 ファイルシステム整合性とDB整合性は別

再起動ありのAMI作成は、ファイルシステムを静止した状態でスナップショットを取得するための選択です。ただし、ファイルシステムが整合していることと、データベースが業務上正しい時点へ必ず復旧できることは同義ではありません。

DB固有のログ、トランザクション、外部システムとの連携まで含めたアプリケーション整合性が必要なら、DBの停止・チェックポイント・バックアップ機能や、ベンダー推奨手順を組み合わせます。復元後にアプリとDBを起動して検証する復元テストが不可欠です。

CRASH CONSISTENT書き込み済みデータ

突然電源が落ちた直後に近い状態

FILE SYSTEMファイルシステムを静止

再起動・停止でバッファーを反映

APPLICATIONDBや業務処理も整合

DB固有の静止・バックアップ・検証が必要

この設問が要求しているのはファイルシステム整合性です。そのため、選択肢の中では再起動ありのCreateImageが正解です。本番のPOS・注文DBでは、より強いアプリケーション整合性の要件も別途確認します。

実務編：日次AMIを安全に自動化する

3.1 EventBridge Scheduler → Lambda → CreateImage

毎日決まった時間にAMIを作るなら、EventBridge SchedulerでLambda関数を呼び、LambdaからEC2のCreateImageを実行できます。設問にあるEventBridgeのスケジュールルールでも実現できますが、AWSは現在、より柔軟なEventBridge Schedulerの利用を推奨しています。

Lambdaは対象インスタンスID、一意なAMI名、説明、タグを設定し、NoReboot=Falseで作成します。作成リクエストが成功してもAMIはまずpendingになるため、後続処理ではavailableへの遷移を確認します。

業務影響の小さい時刻とタイムゾーンを設定

02 LAMBDACreateImageを呼ぶ

NoReboot=false、名前・タグ・対象IDを指定

03 EC2 / EBSAMIとスナップショット

状態を監視し、保持期限に従って世代管理

Q6. 毎日AMIを自動作成する構成として最も適切なのは？

3.2 AWS Backupは再起動パラメーターを指定しない

AWS Backupは、EC2と関連EBSボリュームを1つの復旧ポイントとして保護し、スケジュール・保持期間・バックアップボールトを一元管理できます。ただしEC2バックアップはデフォルトで「no reboot」で取得され、バックアッププランにCreateImage APIのNoReboot=falseを指定する欄はありません。

したがって、選択肢にある「AWS Backupのrebootパラメーターを有効化」は成立しません。複数EBSのクラッシュ整合性を持つバックアップにはAWS Backupが便利ですが、今回のように再起動してファイルシステムを静止する要件は、別の制御が必要です。

方法得意なこと今回の注意
CreateImageを直接実行NoRebootを明示してAMI作成動作を制御停止時間、IAM、保持、監視を自分で設計
AWS Backup横断的なスケジュール、保持、ボールト、復旧ポイントEC2はno rebootが既定。プランで再起動を指定しない
DB固有バックアップトランザクションやログを理解した復旧AMIとは別の保持・復旧手順が必要

3.3 最小権限・世代管理・復元試験まで設計する

Lambda実行ロールには、対象EC2のイメージ作成、作成したAMIやスナップショットへのタグ付け、状態確認、期限切れAMIの登録解除とスナップショット削除など、実装に必要な権限だけを与えます。対象をタグで識別し、誤ったインスタンスをバックアップしないようにします。

「毎日作る」だけでは運用は完成しません。保持日数・最低世代数、失敗通知、AMIがavailableになるまでの監視、復元用サブネットでの定期起動、アプリ・DBの検証、古いAMIと関連スナップショットの削除まで決めます。

CREATE作る

日次スケジュール、整合性、タグ、暗号化

RETAIN守る

保持期間、世代数、アクセス制御、失敗通知

RESTORE戻せることを試す

隔離環境で起動し、OS・アプリ・DBを検証

総合演習：POSインスタンスの日次AMI

要件は、①単一EC2に接続された複数EBSを含むAMIを毎日作る、②ファイルシステム整合性を確保する、③手動作業をなくす、の3点です。

LambdaからCreateImageをNoReboot=falseで呼び、EventBridge Schedulerで毎日起動します。AWS Backupのプランには再起動動作を指定できず、NoReboot=trueでは整合性要件を満たしません。

選択肢評価
AWS Backup＋rebootそのようなバックアッププラン設定はない
AWS Backup＋no-reboot設定項目がなく、整合性要件にも合わない
Lambda＋再起動ありCreateImage正解。APIで動作を制御し、日次実行できる
Lambda＋NoReboot=true無停止だがファイルシステム整合性を保証しない

Q10. 要件をすべて満たす最も適切な構成は？

覚え方：AMIは「EC2を起動し直すための設計図＋EBSスナップショット」。整合性を優先するなら再起動あり。APIでは「Reboot=true」ではなく「NoReboot=false」です。

追加演習：AMIのリージョン展開と物理障害分離

カスタムAMIを別リージョンで使う

AMIはリージョン固有です。東京のAMIをシンガポールとシドニーで使うには、それぞれへcopy-imageでコピーします。共有は同一リージョン内の別アカウントへ起動権限を渡す機能で、リージョン間の実体移動ではありません。継続配布はEC2 Image Builderのdistribution settingsも候補です。

9台を障害ドメインへ分散する

ラックレベルのSpread Placement Groupは同一リージョン内の複数AZにまたがれ、各AZで最大7台です。9台なら複数AZへ分けます。現在の公式説明は「各インスタンスを別ラック（独立した電源・ネットワーク）へ配置」であり、「必ず別の物理サーバー」という古い言い換えより、ラック障害の分離として理解します。
