基礎編：EKSとKubernetesの役割を分ける

1.1 EKSはマネージドKubernetes

Amazon Elastic Kubernetes Service（Amazon EKS）は、KubernetesクラスタをAWS上で運用するマネージドサービスです。EKS StandardではAWSがKubernetesのコントロールプレーンを運用し、利用者はアプリケーションとデータプレーンを設計します。

コントロールプレーンにはAPI Server、etcd、Scheduler、Controller Managerなどがあります。データプレーンではNode上のkubeletとコンテナランタイムがPodを実行します。EKS Auto ModeではAWSの管理範囲がNode、ネットワーク、ロードバランシング、ブロックストレージなどへ広がります。

層主な要素EKS Standardの担当
コントロールプレーンAPI Server、etcd、SchedulerAWSが管理
データプレーンNode、kubelet、Pod方式を選び、利用者も運用
アプリケーションDeployment、Service、設定、データ利用者が管理

1.2 Pod、Deployment、Service

Podは1つ以上のコンテナをまとめるKubernetesの最小デプロイ単位です。通常はPodを直接作らず、Deploymentにレプリカ数、コンテナイメージ、更新方法などの望ましい状態を宣言します。

Podは再作成されるとIPが変わり得ます。Serviceはラベルで複数Podを選択し、安定した名前と仮想IPを提供します。HTTPの外部公開にはIngress、TCP/UDPの公開には type: LoadBalancer のServiceを組み合わせます。

応用編：ネットワークと権限を分ける

3.1 VPC CNIとIPアドレス

Amazon VPC CNIは各EC2 NodeへElastic Network Interface（ENI）をアタッチし、各PodへVPCのプライベートIPv4またはIPv6アドレスを割り当てます。PodがVPC内のRDSやS3 Endpointと直接ルーティングしやすい一方、Pod数に応じてサブネットのIPを消費します。

Nodeを増やせない、PodがPendingになる場合は、CPUやメモリだけでなく、利用可能なIP、ENI上限、セキュリティグループ、VPC CNIの状態も確認します。

出典：Amazon VPC CNI

3.2 PodのAWS権限はPod単位で与える

人やCI/CDがKubernetes APIを操作する権限と、PodがS3などのAWS APIを呼ぶ権限は別物です。前者はIAM認証とKubernetes RBAC、後者はKubernetes ServiceAccountへEKS Pod IdentityまたはIRSAを関連付けて制御します。

EKS Pod IdentityではPod Identity Agentと関連付けを使い、対応AWS SDKへ一時クレデンシャルを渡します。AWSは可能な場合にEKS Pod Identityを推奨しています。アプリごとに専用ロールを用意し、必要なS3プレフィックスと操作だけを許可します。

Node IAM Roleをアプリ共通の権限箱にしません。同じNode上の別Podまで権限を得ないよう、ServiceAccount境界で最小権限を設計します。

出典：Kubernetes ServiceAccountでAWSへアクセス

3.3 API Endpointとアプリ公開経路

EKSクラスタのAPI Endpointは kubectl などが操作する管理面の入口です。Public AccessはCIDR制限を行い、Private Accessを有効にするとNodeからAPI Serverへの通信をVPC内に保てます。Private onlyでは管理端末やCI/CDもVPCへ到達できる必要があります。

一方、アプリ利用者の入口はKubernetes IngressやServiceです。AWS Load Balancer ControllerはIngressからALBを、LoadBalancer型ServiceからNLBを作成できます。管理APIと業務アプリの入口を混同しないことが重要です。

出典：EKS API Server Endpoint、AWS Load Balancer Controller

4.1 PodとNodeは別々にスケールする

対象代表機能見るもの
Pod数Horizontal Pod Autoscaler（HPA）CPU、メモリ、カスタムメトリクス
Node数・種類EKS Auto Mode、Karpenter、Cluster Autoscalerスケジュール不能Pod、Node使用状況
リクエスト処理ALB / NLBヘルスチェック、接続、レイテンシ

HPAがPodを増やしても、空きNodeがなければPodはPendingのままです。反対にNodeを増やしても、Deploymentのレプリカ数は自動では増えません。Podの requests を適切に設定し、PodスケールとNodeスケールを組み合わせます。

出典：EKSのNodeオートスケーリング

4.2 アップグレードは一段ずつ進める

Kubernetesの新バージョンではAPI廃止や互換性変更が起こります。EKS Upgrade Insightsとテスト環境で影響を確認し、コントロールプレーンを1マイナーバージョンずつ更新します。

その後、Node、VPC CNI・CoreDNS・kube-proxyなどのAdd-on、アプリケーション、kubectlなどのクライアントを対応させます。PodDisruptionBudget（PDB）、複数レプリカ、Readiness Probeを用意し、Nodeのドレイン中も必要な可用性を維持します。

4.3 ログ・メトリクス・イベントを組み合わせる

EKSのコントロールプレーンログにはAPI Server、Audit、Authenticator、Controller Manager、Schedulerがあります。既定ではCloudWatch Logsへ送信されないため、必要な種類を有効化し、保持期間とコストを設計します。

PodがPendingならKubernetes EventsとSchedulerログ、アプリ異常ならPodログとProbe、Node不足なら容量とIP、権限拒否ならCloudTrailとAuditログを確認します。CloudWatch Observability EKS Add-onを使うと、Container Insightsなどでログ・メトリクス・トレースを収集できます。
