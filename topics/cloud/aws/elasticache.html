基礎

1.1 ElastiCacheとは

Amazon ElastiCacheは、クラウド上で分散インメモリデータストア／キャッシュを構築・運用するフルマネージドサービスです。頻繁に読むデータをメモリへ置くことで、ディスク中心のデータベースより短い応答時間を狙い、元データベースの読み取り負荷を減らします。

1.2 ヒットとミスを体験する

最も基本的なCache-Aside（Lazy Loading）では、アプリが先にキャッシュを見ます。値があればキャッシュヒット、なければキャッシュミスです。ミス時だけ元DBを読み、取得した値をキャッシュへ保存します。

1.3 3つのエンジンを選び分ける

ElastiCacheはValkey、Redis OSS、Memcachedをサポートします。いずれもインメモリのキー・バリューストアですが、データ構造、レプリケーション、永続化、マルチスレッド性能などが異なります。

主な機能レプリカ、Pub/Sub、Sorted Set等レプリカ、Pub/Sub、Sorted Set等シンプルでマルチスレッド
水平分割クラスターモードクラスターモードクライアント側分散
向く用途新規の高機能キャッシュ既存互換性を重視単純な大規模キャッシュ
Valkeyとは？
Valkeyはオープンソースのキー・バリューストアです。ElastiCacheではRedis OSS互換の選択肢として提供され、バージョンに応じてメモリ効率、検索、ベクトル検索などの機能が拡張されています。新規設計ではまずValkeyを候補にし、既存クライアントや機能要件との互換性を検証します。

応用編

応用

2.1 Serverlessとノードベース

ElastiCacheにはServerlessキャッシュとノードベースクラスターがあります。Serverlessは容量計画を減らして自動スケールさせたい場合、ノードベースはノード種別、シャード数、レプリカ数、配置、パラメーターを細かく制御したい場合に向きます。

Serverless
  • 容量を自動管理・自動スケール
  • データを3つのAZへ冗長化
  • 新規・予測困難な負荷に向く
  • 保存量と処理量を軸に課金
ノードベース
  • ノードとトポロジーを指定
  • 性能・可用性・費用を細かく調整
  • 予測可能な負荷に向く
  • パラメーターや配置の自由度が高い
Q3. 新規サービスでアクセス量が読めず、容量計画を最小化したい場合は？

2.2 シャード・レプリカ・Multi-AZ

Valkey／Redis OSSのノードベース構成では、書き込みを受けるプライマリと読み取りに使えるレプリカを組み合わせます。シャードはキー空間を分割して書き込み容量とメモリを水平拡張し、レプリカは読み取り分散と可用性に寄与します。

SHARD
データを分割

書き込みと容量を水平拡張

REPLICA
データを複製

読み取り分散と障害復旧

MULTI-AZ
AZ障害へ備える

別AZのレプリカへ自動フェイルオーバー

レプリカがあればデータ消失はゼロ？
通常のレプリケーションは非同期なので、障害のタイミングによって直近の書き込みが失われる可能性があります。キャッシュとして許容できるかを確認し、厳密な永続性が必要なら元DBを正とするか、対応する耐久性機能を含め別の設計を検討します。

2.3 TTL・無効化・スタンピード対策

キャッシュ設計で難しいのは「入れること」より「いつ捨てるか」です。TTL（Time To Live）は鮮度とヒット率のバランスを決めます。更新時に削除する方式、更新と同時にキャッシュも書き換える方式などを、整合性要件から選びます。

短いTTL

鮮度は高いがミスが増え、DB負荷が上がりやすい。

長いTTL

ヒット率は上がるが、古い値を返すリスクが増える。

TTLジッター

有効期限を少し散らし、同時失効を避ける。

キャッシュスタンピード：人気キーが失効した瞬間、大量リクエストが同時にDBへ向かう現象です。TTLジッター、排他ロック、早期リフレッシュ、古い値の一時提供などで緩和します。

Q5. 大量のキーが同時に失効してDB負荷が急増しました。まず検討する施策は？

2.4 接続とセキュリティ

基本はアプリとキャッシュをネットワーク的に近づけ、必要な送信元だけをセキュリティグループで許可します。Valkey／Redis OSSのノードベースは通常6379、Serverlessは6379と6380、Memcachedは11211と11212を使用します。実際に必要なポートは構成とクライアントの仕様で確認してください。

ネットワーク
  • 送信元SGを参照して最小許可
  • 名前解決可能なエンドポイントを使う
  • 接続プールとタイムアウトを設定
認証・暗号化
  • 転送中暗号化（TLS）
  • 保存時暗号化
  • Valkey／Redis OSSのRBACやIAM認証
Public Endpointは使える？
現在は対応するValkey Serverless構成でPublic接続を選べます。Public EndpointはすべてIAM認証とTLS 1.3が必須です。利便性だけで選ばず、到達経路、認証、監査、レート制限を含めて評価してください。

3.1 設計は「何をキャッシュするか」から

サービス名から構成を選ぶのではなく、データの性質と失敗時の振る舞いから決めます。次のカードを設計順に並べ替えてください。

  • 可用性、暗号化、接続権限を設計する

  • メトリクスと障害時フォールバックを用意する
  • 対象データとキャッシュする目的を決める
  • エンジンとServerless／ノードベースを選ぶ

ドラッグ、または上下ボタンで並べ替えてください。

キャッシュに向くデータ

3.3 高可用性を保ったオンライン垂直スケーリング

オンライン垂直スケーリングは、レプリケーショングループのノード数やAZ分散を減らさず、ノードタイプだけを変更します。ElastiCacheは選択した新タイプのノードを作成してデータを同期し、DNSを新ノードへ更新します。既存のエンドポイント名をアプリ側で変更する必要はありません。

「オンライン」は接続影響ゼロの保証ではありません。公式ドキュメントは最小限のダウンタイムでリクエストを処理し続ける設計としています。低負荷時間帯に実行し、ステージングで試験し、クライアントには短いタイムアウト、再試行、DNS再解決を実装します。自動フェイルオーバー有効クラスターをオンラインのまま変更できる条件として、Valkey 7.2以上またはRedis OSS 5.0.5以上を確認します。

3.4 障害に強いアプリ側の設計

キャッシュは高速ですが、ネットワーク断、フェイルオーバー、スケーリング、メンテナンスによる接続切断は起こり得ます。クライアント側で短い接続・読み取りタイムアウト、指数バックオフ付き再試行、接続プール、DNS再解決を設計します。

フェイルオープン：キャッシュ障害時に元DBへフォールバックするとサービス継続性は上がりますが、全リクエストがDBへ集中する危険があります。レート制限、サーキットブレーカー、古い値の一時利用、段階復旧をセットで考えます。
避けたい実装：タイムアウトなし、無制限再試行、毎回新規接続、全キー同時失効、キャッシュ障害時の無制限DBフォールバック。
Q10. キャッシュ障害に備える実装をすべて選んでください。

総合演習

ケース：セール開始時に商品APIが遅くなる

商品詳細は更新頻度が低く、同じ商品へ大量アクセスがあります。現在は全リクエストがRDSを読み、セール開始直後にDB CPUが上限へ達します。アクセス量の予測は難しく、キャッシュ障害時にもDBを守る必要があります。

設計候補：Serverless Valkey + Cache-Aside、商品ごとのTTL + ジッター、更新イベントによる削除、短いタイムアウト、DBフォールバックのレート制限、ヒット率とEvictionsの監視。
Q11. このケースに最も適した第一案は？
模範的な設計メモ
商品IDをキーにし、初回ミス時だけRDSから取得します。TTLは商品更新許容時間に合わせて設定し、ジッターを加えます。商品更新時は該当キーを削除します。キャッシュ障害時は短いタイムアウト後にDBへフォールバックしますが、DB保護のため同時実行数とレートを制限します。CacheHits / CacheMisses、Evictions、レイテンシー、DB CPUを同じダッシュボードで監視します。

5.1 要件を「性能」と「可用性」に分ける

人気商品の販売開始直後にRDSのCPUが100%へ達し、DBインスタンスを拡張できないなら、読み取りの多い在庫参照をElastiCacheへ逃がしてRDS負荷を減らします。同時に「止められない」という要件には、各シャードのプライマリとレプリカを別AZへ配置し、Multi-AZ自動フェイルオーバーを有効にした構成で応えます。

在庫数をキャッシュだけで確定しない：在庫は誤差が販売超過へ直結します。RDSを正本にし、更新後のキャッシュ削除、短いTTL、書き込みスルー、トランザクション＋Outboxなどから整合性要件に合う方式を選びます。Redis OSSの原子的操作を使う場合も、永続的な注文確定処理と再試行時の冪等性は別に設計します。

5.2 オンラインリシャーディングで止めずに水平拡張

クラスターモード有効のValkey／Redis OSSは、キー空間を16,384個のハッシュスロットに分け、各スロットをシャードへ割り当てます。オンラインリシャーディングでシャードを追加すると、クラスターはリクエストを処理しながらスロットとデータを新しいシャードへ再配置します。これによりメモリ容量だけでなく、読み取り・書き込み処理も複数のプライマリへ分散できます。

BEFORE
2 shards

キー空間を2つのプライマリで担当

RESHARD
スロットを移動

処理継続中にデータを再配分

AFTER
3 shards

容量と読み書き性能を水平拡張

「無停止」は「影響ゼロ」ではありません。リシャーディングは計算負荷が高く、一時的に性能が低下することがあります。クラスタープロトコル対応クライアントを使い、構成エンドポイントからスロット配置を取得し、MOVED応答後にトポロジーを更新できることを事前検証します。
ホットキーの落とし穴：1つの商品キーは1つのハッシュスロット、つまり1つのシャードへ送られます。単一の超人気商品だけに負荷が集中する場合、シャード追加だけでは分散できません。キー分割、ローカルキャッシュ、リクエスト集約、書き込み頻度の抑制も検討します。

出典：AWS公式：クラスターモード有効クラスターのスケーリング、クラスタークライアントのディスカバリ

5.3 Multi-AZ自動フェイルオーバーとリージョン障害

仕組み守る障害切り替え注意点
Multi-AZ + レプリカノード／AZ障害同一リージョン内で自動昇格各シャードに別AZのレプリカが必要
Global Datastoreリージョン障害セカンダリを明示的に昇格クロスリージョン自動フェイルオーバーではない

Multi-AZを有効にすると、プライマリ障害時にレプリケーション遅延が最も小さいレプリカが自動的に昇格します。クラスターモード有効では自動フェイルオーバーが必須ですが、AZ障害へ耐えるにはすべてのシャードに、プライマリと異なるAZのレプリカが必要です。非同期レプリケーションのため、フェイルオーバー時には少量のデータ損失が起こり得る点も織り込みます。

出典：AWS公式：Multi-AZと自動フェイルオーバー、Global Datastoreの前提条件と制約

5.4 提示された「2つ選択」問題の読み解き

想定解の2つ
  • オンラインリシャーディングで、処理を継続しながらシャードを追加できる
  • Multi-AZで、プライマリ障害時にレプリカへ自動フェイルオーバーできる
明確に誤り
  • 単一ノードのコマンド実行をマルチスレッド化するから、という説明
  • 別リージョンへ障害検知だけで自動フェイルオーバーする、という説明
設問上の注意：「データを複数シャードへ分散し、読み取りと書き込みの負荷を並列に処理できる」という選択肢も、AWSの仕様としては正しい記述です。クラスターモードは水平分割によってストレージ容量とスループットを拡張します。そのため、選択肢がこの文面のままで「2つだけ選択」なら設問は曖昧です。想定解を選ぶ試験対策と、実際の仕様判断を混同しないようにしましょう。
