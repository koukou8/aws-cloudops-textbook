基礎編

基礎

1.1 IAMは「AWSリソースへのアクセス」を管理する

IAMはIdentity and Access Managementの略です。AWSのサービスやデータへ、誰がどの操作を行えるかを管理します。EC2を停止する、S3オブジェクトを読む、IAMロールを作る、といった操作を必要な範囲に限定できます。

ここで分けたいのが認証（Authentication）と認可（Authorization）です。認証は「あなたは誰か」を確かめること、認可は「その操作をしてよいか」を判断することです。社員証で入館できても、すべての部屋に入れるとは限らない、と考えると分かりやすくなります。

認証

本人確認

社内IDとMFAでログインし、どの利用者のセッションかを確かめる。

認可

操作の許可

そのセッションでS3を読めるか、書けるか、削除できるかを判定する。

1.2 ユーザー・グループ・ロール・ポリシー

用語役割押さえる点
rootユーザーAWSアカウントの最初の強い権限を持つID日常業務に使わず、厳重に保護する
IAMユーザーアカウント内に作るID必要に応じてパスワードや長期アクセスキーを持てる
IAMユーザーグループ複数のIAMユーザーへ権限をまとめて付与グループ自体でログインしない。IAMロールをメンバーにはできない
IAMロール許可された利用者やサービスが引き受ける権限の単位通常のパスワード・長期アクセスキーを持たず、一時セッションで使う
IAMポリシーどの操作・リソースを許可／拒否するかのルールJSON形式でAction、Resource、Conditionなどを指定する

現在、従業員のアクセスにはフェデレーションと一時的な認証情報、EC2やLambdaなどの処理にはIAMロールの利用が推奨されます。IAMユーザーは、ロールやフェデレーションを利用できない用途などで検討します。

「グループ」は3種類を区別します。LDAPのグループ、IAM Identity Centerのグループ、IAMユーザーグループは別の仕組みです。画像の構成は、LDAPグループのメンバーに対応するIAMロールをIdPで選ぶもので、LDAPグループをIAMユーザーグループへ自動変換する意味ではありません。

出典：IAM roles、IAM user groups

1.3 ロールの「信頼」と「権限」は別の設定

信頼ポリシー

誰がこのロールを引き受けてよいかを定義します。例：登録したSAML IdPからのフェデレーションを許可する。

権限ポリシー

引き受けた後に何をしてよいかを定義します。例：開発用S3オブジェクトだけ読み書きできる。

ロールを引き受けると、AWS STS（Security Token Service）などの仕組みで一時的な認証情報を使うセッションが成立します。API利用時の一時認証情報には、アクセスキーID、シークレットアクセスキー、セッショントークンが含まれ、有効期限があります。

ロールがS3の操作権限を持っていても、そのロールを引き受けるための信頼関係や条件を満たさなければ使えません。逆にロールを引き受けられても、操作するリソースに対する権限がなければアクセスは拒否されます。

出典：IAMロールと一時認証情報、SAMLロールの信頼関係

応用

2.1 JSONポリシーを読む

次は「example-company-dataバケットのdev/配下にあるオブジェクトを読む」権限を付与する、IDベースポリシーの例です。

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-company-data/dev/*"
  }]
}
項目意味読み方
Versionポリシー言語のバージョン2012-10-17は作成日ではない
Statement / Effectルールと、その効果Allowは許可、Denyは拒否
Action対象の操作s3:GetObjectはオブジェクトの取得
Resource対象リソースARNでバケットやオブジェクト等を指定
Condition追加条件。必要な場合に指定要求元、タグ、時刻など、対応する条件キーを使う
Principal誰を対象とするか信頼ポリシーやS3バケットポリシー等で使う。上のIDベース例には書かない
S3でよくある間違い：GetObjectにはオブジェクトARN（バケット名の後に /キー名）、ListBucketにはバケットARNを指定します。上の例だけでは一覧取得の権限はありません。暗号化キー等、別の許可が必要な操作もあります。

出典：IAM JSON policy elements

2.2 AllowとDenyの判定を体験する

基本は「許可されていない要求は拒否する」です。これを暗黙的Denyと呼びます。要求に一致するAllowがあると許可の候補になり、適用される明示的Denyがあれば拒否が優先します。

実際のAWSでは、リソースベースポリシー、アクセス許可境界、セッションポリシー、OrganizationsのSCP／RCP、KMSのキーポリシーなども関わります。単に「どこかにAllowが1つあれば必ず成功」とは判断できません。

社内グループ→ロール→操作権限のデモ

同一アカウントのIDベースポリシーだけを扱う学習モデルです。信頼・認証はチェック欄で簡略化し、リソースポリシー、SCP、境界、KMS等は評価しません。AWS公式シミュレーターや実アカウントへの操作ではありません。

利用するロール：DevRole

設定に応じて判定します。
    このグループに対応するデモ用ポリシー
    
              
    DevRoleはdev/配下の読み書き・削除、AuditRoleはバケット内オブジェクトの読み取りを許可します。実務ではデータの必要範囲に合わせてさらに絞り込みます。
    
            
    
            
    順に試してみましょう。①開発者でprod/を読む → 暗黙的Deny。②開発者でdev/を削除 → Allow。③削除Denyを追加 → 明示的Deny。④「IdPで本人確認」を外す → ロールセッションが成立せず、操作の認可へ進みません。

    2.3 LDAPとSAMLで既存の社内認証を使う
    
            
    LDAPは、ディレクトリの利用者・グループ情報へアクセスするためのプロトコルです。LDAP対応のディレクトリが、そのままAWSへSAML認証結果を渡せるとは限りません。そこで、LDAPと連携するIdP（Identity Provider：IDプロバイダー）を使います。
    SAMLは、IdPで確認した本人情報や属性を、署名付きの認証応答でサービス側へ伝える標準です。別の認証基盤で確認したIDをAWSでも利用する連携を、フェデレーションと呼びます。
    
            
    01 社内で本人確認LDAPディレクトリ
    利用者とグループ所属を管理する
    02 認証結果を発行SAML IdP
    グループに応じたロール情報をSAML応答へ設定する
    03 ロールの利用を許可AWSのSAML連携・STS
    署名・有効期限・信頼条件などを確認し、一時セッションへつなぐ
    04 操作を認可IAMロールの権限
    許可された範囲でS3等へアクセスする
    
            
    事前にIAMへIdPのメタデータを登録し、職務別のIAMロールを作り、そのIdPを信頼するよう設定します。IdP側ではLDAPグループに応じて、SAMLのRole属性へ許可するIAMロールARNとSAMLプロバイダーARNの組を設定します。
    API利用では、SAML応答を使ってSTSの AssumeRoleWithSAML で一時認証情報を取得できます。コンソールSSOでは、ブラウザがAWSのサインインエンドポイントへSAML応答を送り、AWS側がセッションへつなぎます。
    
            
    パスワードをAWSへコピーする必要はありません。本人確認は社内IdP側で行い、AWS側はSAML応答と信頼関係に基づいてアクセスを認めます。LDAPグループに追加しただけで権限が自動的に生えるのではなく、IdPでのロール割り当てとAWS側の設定が必要です。
    
            
    出典：SAML 2.0 federation、SAMLのRole属性、コンソールへのSSO
    
            
    
              
    Q6. 設定済みのSAML連携で、実行時の流れを並べ替えてください。
    
              
    • AWS側で応答と信頼条件を確認し、ロールセッションを成立させる
    • IdPがLDAP等を使って本人を確認する
    • AWSリソースへの要求を、ロールの権限などで判定する
    • IdPがグループに応じたロール情報を含むSAML応答を作る
    
              
    ドラッグまたは矢印ボタンで変更すると判定します。

    3.1 IAM Identity Centerではどう構成する？
    
            
    従業員が複数のAWSアカウントやアプリを使う場合、IAM Identity Centerでアクセスを集中管理する構成が推奨されます。IDソースには、Identity Center自身のディレクトリ、対応するMicrosoft Active Directory、外部IdPを選べます。
    画像のように既存LDAPを使いたいなら、LDAPと連携する外部IdPを経由してIdentity CenterへSAML連携する構成が候補になります。ユーザー・グループ情報をIdentity Centerへ登録し、AWSアカウントへの割り当てを管理します。
    
            
    仕組み役割混同しない点
    SAML 2.0外部IdPでの認証結果を使ってSSOするユーザー一覧・所属グループを問い合わせて同期する仕組みではない
    SCIMユーザー・グループ情報をプロビジョニングするログイン時の認証プロトコルとは異なる。対応IdPで利用する
    アクセス許可セットAWSアカウントで使う権限のテンプレート割り当てに応じ、Identity Centerが対象アカウントのIAMロールを管理する
    グループへの割り当てどのAWSアカウントで、どの権限を使えるかを決める社内LDAPグループとIAMユーザーグループは別物
    
            
    選択肢1が不適切な理由：任意のオンプレミスLDAPを、そのままIdentity Centerの同期先として指定できるわけではありません。対応するActive Directory連携と、一般的なLDAPディレクトリは区別します。Identity Center自体が不適切なのではなく、選択肢の直接連携の説明が不十分です。
    
            
    出典：Identity CenterのIDソース、外部IdPとプロビジョニング、アクセス許可セット

    3.2 最小権限と、入社・異動・退職の運用
    
            
    職務に必要な操作・リソース・条件へ絞る考え方を、最小権限と呼びます。たとえば「監査担当は必要なログの参照のみ」「開発者は開発環境へ変更可能」「本番変更は別ロール」という形で責任を分けます。
    人のアクセスにはフェデレーションとMFA、アプリにはロールを使い、長期アクセスキーを配布する範囲を減らします。EC2へキーを書き込む代わりにインスタンスプロファイル、Lambdaには実行ロールなどを使います。
    
            
    場面行うこと確認すること
    入社社内IDと職務グループ、必要なアカウントへの割り当てを用意不要な管理権限が付いていないか
    異動旧グループ・割り当てを外し、新しい職務へ変更権限が追加される一方になっていないか
    退職・緊急停止IdP側の利用停止と割り当て解除、必要に応じたセッション対処すでに発行したセッションが残っていないか
    定期棚卸し未使用ロール、アクセスキー、過剰な許可を見直すAccess Analyzerや利用履歴で必要性を判断する
    
            
    グループから外した瞬間に、すべての既存セッションが消えるとは限りません。新しいセッションの発行停止と、発行済みセッションの権限・有効期限を分けて考えます。緊急時は利用方式に対応した失効手順を確認します。直接SAMLで使うIAMロールと、Identity Centerの許可セット由来のセッションでは、管理手順も異なります。
    
            
    出典：IAMの推奨事項、ロールの一時セッションへの対処

    3.3 AccessDeniedを順に切り分ける
    
            
    最初に「今どのID・ロールで操作しているか」を確かめます。意図したグループに属していても、違うAWSアカウントやロールのセッションを使っていることがあります。
    
            
    # 現在のCLI認証情報で使っている主体を確認（参照操作）
aws sts get-caller-identity

# Identity Centerの設定済みプロファイルを使う場合
aws sso login --profile company-dev
aws sts get-caller-identity --profile company-dev
    
            
    止まっている場所確認すること
    IdPでログインできない社内ID、MFA、アカウント状態、IdPへの到達性
    SAML連携が失敗する署名証明書、有効期限、受信先、IdPメタデータ、Role属性と信頼ポリシー
    ロールを選べないLDAPグループのマッピング、IdPの割り当て、Identity Centerへの同期と割り当て
    ロール利用後にAccessDeniedAction、Resource、Condition、明示的Deny、境界・SCP等、リソース側の許可
    一部のS3処理だけ失敗するListBucketとGetObjectの違い、オブジェクトARN、KMS権限など
    
            
    CloudTrailではAssumedRoleなどの実行主体と、操作名・対象・エラーを調べます。IAMポリシーの構文・権限検証にはAccess Analyzerや公式のポリシーシミュレーターも使えます。ただしシミュレーターが扱える範囲には制限があるため、対象環境の条件を合わせて判断します。
    
            
    Direct Connectの役割：オンプレミスとAWSをつなぐネットワーク経路です。通信できることとAWSの操作権限は別です。Direct Connectを接続しただけでは、IAMロールがLDAPパスワードを検証するようにはなりません。
    
            
    出典：ポリシー評価、IAMポリシーシミュレーター

    総合演習：画像の設問を解く
    
        
    
          
    既存LDAPとグループ所属を使い、職務別にアクセスを許可する
    
          
    選択肢判断理由
    1. Identity CenterへLDAPをそのまま同期説明が不適切任意のLDAPを直接指定できるわけではない。対応AD連携や外部IdP経由の構成を区別する必要がある
    2. LambdaでIAMユーザーを複製最適ではないIAMユーザーを作るだけではLDAPでの認証連携にならず、認証情報や削除・同期の運用も増える
    3. CloudFormation＋Direct Connect要件を満たさないロールの構築とネットワーク接続だけでは、LDAPからAWSへの認証連携を実現できない
    4. LDAPと連携するSAML IdP＋IAMロール正解既存の本人確認を利用し、グループに応じたロールとポリシーで最小権限を実現できる
    
          
    要件と仕組みの対応：既存認証情報の再利用はIdP／フェデレーション、職務別アクセスはグループのマッピングとIAMロールの権限で実現します。新規の全社的なアクセス管理では、そのIdPとIAM Identity Centerを組み合わせる構成も検討します。

    追加演習：IAM Identity Centerと外部SAML IdP
    
        
    
          
    接続ではメタデータを相互交換します。IAM Identity Centerが生成するSPメタデータ（Entity ID、ACS URL等）を外部IdPへ登録し、外部IdPのSAMLメタデータ（SSO URL、署名検証用X.509証明書等）をIdentity Centerへ取り込みます。固定IP一覧、全メンバーアカウントの管理者権限、管理アカウントのルート資格情報は前提ではありません。
    
          
    別の論点：認証の信頼確立と、ユーザー／グループのプロビジョニングは別です。外部IdPがSCIMをサポートする場合は、自動プロビジョニングも合わせて設計します。
