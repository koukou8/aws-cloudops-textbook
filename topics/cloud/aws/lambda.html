基礎編

基礎

1.1 Lambdaは、イベントに応じてコードを動かす

AWS Lambdaは、サーバーの台数やOSの保守を利用者が直接管理せず、コードを実行できるサーバーレスのコンピューティングサービスです。関数へコードを配置し、ファイルのアップロード、API要求、メッセージの到着などをきっかけに実行します。

サーバーレスでも実際にはサーバー上で動きます。AWSが基盤を管理する一方で、利用者はコード、依存ライブラリ、IAM権限、タイムアウト、容量などを設計します。

1.2 関数、ハンドラー、実行環境

関数を呼び出すと、Lambdaはイベントをコードの入口であるハンドラーへ渡します。イベントには、たとえば入力動画のS3バケット名とオブジェクトキーが含まれます。実行環境はランタイム、コード、ライブラリなどを読み込んでからハンドラーを動かします。

新しく実行環境を初期化する際の開始遅延を、コールドスタートと呼びます。同じ実行環境が再利用されると、初期化を省ける場合があります。ただし再利用は保証されないので、必要な永続データはS3やDynamoDBなどへ保存します。

1.3 呼び出し方で、待ち方と再試行が変わる

方式動き例と失敗時の扱い
同期呼び出し呼び出し元が処理結果を待つAPI要求など。呼び出し元や連携サービスがエラー・再試行を扱う

業務全体が非同期でも、関数の呼び出しがLambdaの「非同期呼び出し」とは限りません。たとえばSQSのイベントソースマッピングは、Lambdaがメッセージを読み、関数を同期的に呼び出して結果を確認します。

そのため、関数の非同期DLQ設定と、SQSキューのredrive policyによるDLQは別の仕組みです。DLQは処理できなかったイベントの回収に使いますが、同時実行の専用枠を増やす設定ではありません。

応用編：同時実行の容量設計

応用

2.1 同時実行数と「毎秒何件」は違う

同時実行数は、ある瞬間に処理中の要求数です。毎秒の受付件数（RPS）ではありません。通常のオンデマンド実行では、1つの実行環境が同時に1つの要求を処理し、並列要求に応じて複数環境へ広がります。

容量の概算には、平均同時実行数 ≈ 毎秒の平均到着数 × 平均処理時間（秒）を使います。毎秒200件が到着し、平均2秒かかるなら、およそ400の同時実行が必要です。

平均到着数

200件/秒

平均処理時間

2秒

平均同時実行数の概算

400

これは平均値の目安です。実際には到着の偏り、長い処理、再試行、ソース側の制約も見ます。短時間の関数では、同時実行枠が余っていても、別のRPS制限へ到達する場合があります。

出典：同時実行数の考え方とRPS

毎秒100件、平均処理時間4秒なら、平均同時実行数の概算は です。

2.2 予約済みとプロビジョンドを使い分ける

比較予約済み同時実行数プロビジョンド同時実行数
主な目的その関数だけの同時実行枠を確保し、上限も設定実行環境を事前に初期化し、開始時の遅延を抑える
400にすると400枠を占有し、400を超えて実行しない事前初期化した環境を400用意する
コールドスタート初期化を省く設定ではない用意した環境で処理する範囲の初期化遅延を抑える
設定単位関数単位公開バージョン／エイリアス。$LATESTには設定不可
追加料金設定自体の追加料金なし。通常の実行料金は発生事前確保する容量に追加料金が発生

プロビジョンド同時実行数もアカウントの容量を消費します。ただし、それを超えた要求をオンデマンドで処理できる場合があり、関数の明確な上限を設定する予約済み同時実行数とは役割が異なります。

必要なら両方を組み合わせられます。予約済み同時実行数が設定されている関数では、プロビジョンド同時実行数の合計はその予約枠を超えられません。画像のような「他の関数に左右されない専用の400枠」が要件なら、まず予約済み同時実行数を設定します。

他の関数が忙しくても、400枠は使える？

プロビジョンド同時実行数を使わない静的な学習モデルです。「予約なし」の比較では、他の共有関数が先に枠を使った状況を仮定します。実際のスケジューリング、初期化、RPS、ソース側の制限は再現しません。

紫：他関数の予約 100 ／青：対象関数の予約 400 ／灰：残る共有枠 500

対象関数に予約なし

100 / 400 を実行可能

直ちに実行できない対象要求：300
他の共有関数が使う枠：800

対象関数に予約あり

400 / 400 を実行可能

直ちに実行できない対象要求：0
他の共有関数が使える枠：500

入力に応じて比較します。
試すポイント：他の共有関数の要求を増やしても、予約後の対象関数の枠は変わりません。次にサムネイル要求を500へ増やすと、予約400が上限であることを確認できます。予約を0にした場合は「予約なし」ではなく、この関数の新たな実行を止める設定です。

2.3 アカウント上限・共有枠・スケーリング速度

標準的な同時実行数クォータは、アカウント・リージョンあたり1,000です。ただし新しいアカウントでは初期クォータが低い場合があり、引き上げ済みならその適用値が使われます。

予約枠を割り当てる際は、未予約の関数用に少なくとも100枠を残す必要があります。他の予約が100あり、上限1,000から対象へ400を確保するなら、残る未予約プールは500です。すべての予約・事前確保の設定を確認して計算します。

一方、スケーリング速度は「新しい実行環境をどれだけ速く増やせるか」です。通常のオンデマンド関数では、各関数で10秒ごとに最大1,000環境を増やすスケーリングレートがあります。専用枠を確保しても、初期化や急激な負荷増加、イベントソース、接続先の制約は別に残ります。

画像の「常に400」の意味：他の関数に奪われない同時実行枠を確保することです。「400件が常に実行中」「400件がゼロ遅延で開始」「下流サービスも400並列に耐える」という意味ではありません。

出典：Lambdaクォータ、スケーリング速度

実務

3.1 予約済み400を設定する

Lambdaの関数を開き、設定（Configuration）→同時実行（Concurrency）で予約済み同時実行数を設定します。アカウント上限と他の予約設定を先に確認してください。CLIでは次の操作に相当します。

# アカウントの適用上限などを確認（参照操作）
aws lambda get-account-settings --region ap-northeast-1

# 対象関数の予約済み同時実行数を400へ変更（設定変更）
aws lambda put-function-concurrency \
  --function-name thumbnail-generator \
  --reserved-concurrent-executions 400 \
  --region ap-northeast-1

# 設定した値を確認（参照操作）
aws lambda get-function-concurrency \
  --function-name thumbnail-generator \
  --region ap-northeast-1

返却される ReservedConcurrentExecutions が400か確認します。アカウント上限を上げただけでは、この関数に専用枠を配分したことにはなりません。

コールドスタート低減も必要なら、公開バージョンやエイリアスへプロビジョンド同時実行数を追加し、そのエイリアスを呼び出すよう設定します。別名や$LATESTを呼んでいると、用意した環境が使われない場合があります。

出典：予約済み同時実行数の設定、プロビジョンド設定と呼び出し先

3.2 サムネイル処理の失敗・重複・権限を設計する

設計点行うこと理由
入力と出力の分離別バケットか、入力用プレフィックスだけにトリガーを限定出力画像の保存で再び起動するループを防ぐ
冪等性動画の識別子・バージョン等を使い、同じイベントの再処理を考慮イベントの重複や再試行があっても、不要な重複結果を作らない
失敗の回収非同期のon-failure destinationやDLQ等を設定再試行後も失敗したイベントを調査・再処理する
実行ロール入力のGetObject、出力のPutObject、必要なログ・KMS等の権限関数が処理に必要なリソースだけを操作できるようにする
呼び出しの権限S3から関数を呼べるリソースベースポリシー関数がS3を読む権限とは別の許可が必要

非同期呼び出しでは、関数エラー時に既定で2回の追加試行があります。スロットリングやシステムエラーでは別の再試行規則が使われ、既定では最大6時間再試行されます。イベント有効期限や再試行設定も合わせて確認します。

再試行は、同時実行枠の確保や冪等性を不要にしません。動画が大きい場合は、ライブラリの配布方法、一時領域、処理時間を測定し、通常のLambda実行に収まる単位へ処理を分割するなどの設計を行います。

2種類の許可を確認：「S3がLambdaを呼び出せる」と「LambdaがS3の動画を読める」は別です。後者には関数の実行ロールを使います。IAM教材の「誰が何をできるか」の考え方が、そのまま当てはまります。

3.3 監視と性能の調整

メトリクス・情報見ること
ConcurrentExecutions実際の同時実行数。予約上限へ張り付いていないか
Throttles実行前に制限された呼び出し。関数コードのErrorsとは別に確認
Duration / Errors処理時間、タイムアウト、実行中のエラー
AsyncEventAge等非同期イベントの待ち時間。容量不足で処理が遅れていないか
ログのメモリ使用量・下流側メトリクスメモリ不足、S3やDB等の応答遅延・接続制約

処理時間が伸びると、同じ到着量でも必要な同時実行数が増えます。メモリ・CPUや依存先を調整して短縮できれば、必要容量が減る可能性があります。性能と実行コストを測定して判断します。

予約枠を大きくすると、別の関数が使える共有枠は減ります。また、Lambdaから400本同時にDB接続するなど、下流側へ負荷を集中させる場合があります。必要な専用枠を確保しつつ、接続数やキュー処理の並列度も合わせて調整します。

総合演習：画像の設問を解く

サムネイル関数へ、他のアプリに左右されない400枠を確保する

問題では、アカウント・リージョンのクォータ引き上げは完了しています。残っているのは、共有枠から対象関数専用の容量を確保する設定です。

選択肢判断理由
1. DLQを設定目的が異なる失敗イベントの回収・再処理に使う。専用の同時実行枠は確保しない
2. 予約済み同時実行数400正解他関数が使えない400枠を確保し、対象関数の上限も400にする
3. プロビジョンド同時実行数400この設問の狙いとは異なる主な目的は事前初期化による開始遅延の低減。今回求められた専用枠と上限の制御には予約済みを使う
4. メモリを増やす目的が異なる処理性能に影響するが、他関数から独立した400枠を取り分けない
予約済み400の効果：「他の関数から守る」と同時に「この関数が400を超えて増えないようにする」です。起動の遅延も抑えたいという別の要件が加われば、プロビジョンド同時実行数の併用を検討します。

追加演習：イベントが来ないことを監視する

S3への1時間ごとのファイル到着でLambdaが必ず起動する構成なら、AWS/LambdaのInvocationsを1時間単位で合計し、「1未満」でアラームにします。呼び出しがない期間はデータ点自体がない場合があるため、欠損データをbreachingとして扱い、SNSへ通知します。

適用条件：同じ関数が別イベントでも起動する、店舗ごとの欠損を個別検知したい、遅着許容時間が異なる場合は、店舗ID別カスタムメトリクスやEventBridge Schedulerによる到着台帳確認へ発展させます。
