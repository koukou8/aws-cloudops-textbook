今回のIPv6設問

Egress-only Internet GatewayをVPCへ作成し、プライベートサブネットの ::/0 を向けます。

NAT Gatewayは「IPv4専用」なのか

ネイティブIPv6インターネット通信のデフォルトルートをNAT Gatewayへ向けることはできません。一方、既存のNAT GatewayにはNAT64が自動的に備わっており、DNS64が合成した 64:ff9b::/96 宛ての通信をIPv4へ変換できます。つまり「IPv6の出口」ではなく「IPv6からIPv4専用宛先へ渡す変換器」として使います。

2.1 VGWとCGWはVPNの両端

AWS Site-to-Site VPNでは、AWS側の終端としてVirtual Private Gateway（VGW）またはTransit Gatewayを使います。Virtual Private GatewayはVPCへアタッチするVPNコンセントレータです。

2.2 Transit Gatewayはネットワークのハブ

VPCが増えると、VPC Peeringを総当たりで張る構成は接続数とルート管理が複雑になります。Transit Gateway（TGW）はVPC、VPN、Direct Connect Gateway、別TGWなどをアタッチする中継ハブです。

TGW自身のルートテーブルで、どのアタッチメントからどこへ転送できるかを分離できます。ただし、VPCサブネット側のルート表にもTGWへのルートが必要です。CIDRの重複は避けます。

通信は自動的に許可されません。VPCルート表、TGWルート表、戻り経路、セキュリティグループ／NACLを順番に確認します。

2.3 マルチアカウント・マルチリージョンのTransit Gateway

Transit Gatewayはリージョン単位のハブです。中央アカウントに1つだけTGWを作っても、4リージョンのVPCをその1台へ直接アタッチする構成にはできません。ワークロードを配置する各リージョンにTGWを作り、そのリージョンのVPCをアタッチします。

AWS Organizations配下の別アカウントへは、AWS Resource Access Manager（AWS RAM）でTGWを共有できます。VPC所有アカウントは共有されたTGWへのVPCアタッチメントを作成でき、TGW所有アカウントがルートテーブルの関連付け・伝播・静的ルートを中央管理します。

実務編：AWSサービスと検査装置へつなぐ

3.1 Gateway VPC EndpointはS3／DynamoDB専用

Gateway VPC Endpointを使うと、VPCからS3またはDynamoDBへ、IGWやNATデバイスを使わず到達できます。対象ルート表にはAWS管理プレフィックスリストを宛先、エンドポイントをターゲットとするルートが追加されます。追加料金はありません。

その他の多くのAWSサービスはInterface VPC Endpointを使います。Interface Endpointはサブネット内にプライベートIPを持つENIを作成し、PrivateLinkでサービスへ接続します。名前は似ていますが経路の作り方が異なります。

種類対象配置・経路主な制御
Gateway EndpointS3、DynamoDBルート表＋プレフィックスリストEndpoint Policy
Interface Endpoint対応する多数のサービスサブネットのENI／DNSSecurity Group＋Endpoint Policy

3.2 Direct ConnectからS3へ：Interface Endpointを選ぶ

オンプレミスのポータルがDirect Connect経由でS3へ接続し、通信をプライベートIPとAWSネットワーク内に閉じたい場合は、S3用のInterface VPC Endpoint（AWS PrivateLink）を使います。エンドポイントは選択したサブネットにプライベートIPを持つENIを作るため、オンプレミスからPrivate VIFまたはTransit VIF経由でそのENIへ到達できます。

S3 Gateway Endpointは無料でVPC内のワークロードに適していますが、ルート表へ追加した経路をDirect Connect、VPN、VPC Peering、Transit Gatewayの反対側へ延長できません。したがって「Direct ConnectがあるからGateway Endpointも使える」とは判断しません。

Gateway型とInterface型を併用して料金を最適化する
同じVPCに両方を作成できます。S3 Interface Endpointで「Private DNS only for inbound Resolver endpoint」を使うと、オンプレミスからのDNS問い合わせはInterface EndpointのプライベートIPへ、VPC内からの問い合わせは追加料金のないGateway Endpointへ誘導できます。この設定には同じVPCのS3 Gateway Endpointが必要です。

アクセス制御：Endpoint Policyで利用可能なS3操作・バケットを絞り、S3バケットポリシーでは必要に応じて aws:SourceVpce で当該Interface Endpoint経由だけを許可します。誤設定するとAWSコンソールや別経路からのデータアクセスも拒否するため、管理経路と復旧手順を先に確認します。

選択肢の読み方：S3 Transfer Accelerationは遠距離転送の高速化、パススタイルURLは名前の表記方法です。どちらもPrivate VIFからプライベートIPでS3へ接続する経路にはなりません。なおPublic VIFならS3のパブリックIPへDirect Connect経由で到達できるため、「S3のパブリックエンドポイントは必ずインターネット経由」と覚えるのも誤りです。今回の選択肢では、プライベートIPとPrivateLinkを使えるInterface Endpointが要件に最も合います。

追加演習：VPNのNAT越えとNAT Gateway移行

Customer GatewayがNATの背後にある

Customer Gatewayリソースには、AWS側から見えるNATデバイスの静的パブリックIPを指定します。オンプレミス機器のプライベートIPやMACアドレスではありません。機器とNATがNAT Traversal（UDP 4500）を通せること、必要なUDP 500/4500と経路も確認します。

NAT InstanceからNAT Gatewayへ移行後に通信不能

まずNAT GatewayがAvailableか、パブリックサブネットとElastic IP、プライベートサブネットのルートが正しいか確認します。NAT GatewayはTCP、UDP、ICMPを扱いますが、NAT Instanceのカスタム設定で通していたGREやIPsec等は代替できません。NAT Gatewayにはセキュリティグループを関連付けません。
