1.1 RDSが管理するもの、利用者が管理するもの

Amazon Relational Database Service（Amazon RDS）は、AWS上でリレーショナルデータベースのセットアップ、運用、スケーリングを容易にするマネージドサービスです。Db2、MariaDB、Microsoft SQL Server、MySQL、Oracle Database、PostgreSQLを選択できます。

応用編：可用性と読み取り性能を分ける

2.1 Multi-AZは高可用性

Multi-AZ DBインスタンス配置では、別のアベイラビリティーゾーン（AZ）に同期スタンバイを維持します。プライマリやAZに問題が起きると、RDSがフェイルオーバーします。

スタンバイは通常の読み取りクエリを受け付けません。そのため、Multi-AZは読み取りスケーリングではなく、高可用性と耐障害性のための構成です。

2.2 リードレプリカは読み取りスケール

リードレプリカはプライマリの読み取り専用コピーです。レポート、検索、集計などをレプリカへ振り分け、プライマリの負荷を下げます。更新はプライマリから非同期で複製されるため、反映遅延を前提にします。

Multi-AZのスタンバイとリードレプリカは役割が異なります。高可用性にはMulti-AZ、読み取り性能にはリードレプリカを選び、必要なら組み合わせます。

5.1 IOPSとスループットを分けて測る

IOPSは1秒あたりのI/O操作回数、スループットは1秒あたりに転送するデータ量です。小さいランダムI/Oが多い処理はIOPS、大きな連続I/Oはスループットが先に上限へ達することがあります。「ストレージが遅い」だけでは、どちらを増やすべきか確定できません。

CloudWatchではReadIOPS・WriteIOPS、ReadThroughput・WriteThroughput、ReadLatency・WriteLatency、DiskQueueDepth、BurstBalanceを同じ時間帯で確認します。対応するインスタンスではEBSIOBalance%とEBSByteBalance%も参考になります。CPUUtilization、FreeableMemory、DatabaseConnections、上位SQLや待機イベントも並べ、別レイヤーの飽和を除外します。

観測主な示唆
IOPSが上限付近、待ち行列とレイテンシ増IOPS不足を疑う
Read/WriteThroughputが上限付近MiB/sの帯域不足を疑う
BurstBalanceが枯渇gp2のバースト依存を疑う
CPUが飽和しI/Oは余裕DBクラスやSQLを調べる
読み取りSQLだけが支配的キャッシュ・索引・リードレプリカも候補
db.t3.mediumも無関係ではありません。DBインスタンスクラスにはEBS帯域の上限があり、プロビジョニングしたストレージ性能をクラス側が使い切れない場合があります。ストレージとインスタンスクラスの上限を両方確認します。

出典：RDSのCloudWatchメトリクス、RDSストレージと性能上限

5.2 gp2・gp3・io1・io2を比較する

タイプ性能の考え方現在の位置づけ
gp2容量に応じるベースラインIOPSとバーストクレジット前世代。小容量で持続負荷なら枯渇に注意
gp3基本3,000 IOPS・125 MiB/s。容量と独立して追加性能を設定可能汎用SSDの推奨。費用対性能を比較
io1必要なIOPSをプロビジョニングし、持続性能を得る前世代。今回の選択肢では正解
io2 Block Express高IOPS・高スループット・低レイテンシと高耐久性I/O集約・レイテンシ重視でAWSが推奨

RDS for MySQLのio1／io2では、条件を満たせば最大256,000 IOPSを設定できます。ただし最大値はストレージ容量、IOPS対GiB比、DBインスタンスがNitroベースか、インスタンスクラスの帯域などに左右されます。「タイプを選べば必ず最大性能が出る」という意味ではありません。

gp3はIOPSとストレージスループットを追加プロビジョニングできるため、必要性能がgp3の範囲内ならio系より費用対効果が高い場合があります。持続的で高いIOPS、低レイテンシ、より高い耐久性が必要ならio2を検討します。

既存DBのストレージタイプ変更は無停止？
ストレージタイプの変更では、処理開始時に短いダウンタイムが発生する場合があります。その後はDBを利用しながらstorage-optimizationが進みます。変更中は次のストレージ変更を行えない期間があるため、検証、バックアップ、保守時間、アプリの再接続を計画します。

出典：gp3・io1・io2の比較、ストレージ変更の影響

5.3 設問の答えと、実環境での判断

設問では、gp2を使用中で、原因がストレージI/O性能だと特定されています。提示された4つの選択肢のうち、ストレージ性能を直接プロビジョニングするio1への変更が正解です。

ただし実環境では、gp3へ移行して必要なIOPS／スループットを追加する案と、io2 Block Expressを必ず比較します。読み取りレプリカは読み取りI/Oを別インスタンスへ逃がせるため、読み取り中心なら効果があり得ますが、書き込み性能や元DBのストレージ上限を直接増やす手段ではありません。キャッシュやインデックスもI/O削減には有効ですが、測定した上限そのものを引き上げる変更ではありません。

追加実務演習：Aurora Global DatabaseとリージョンDR

実務

6.1 RPO・RTOと障害の範囲を先に読む

RPO（目標復旧時点）は許容できるデータ損失の時間、RTO（目標復旧時間）はサービスを復旧させるまでの時間です。RPO 15秒は「障害発生直前から最大15秒分までのデータ損失を許容する」という意味で、15秒以内にサービスを再開するという意味ではありません。

設問がリージョン全体の障害を対象にするなら、同一リージョン内のAZだけに複製するMulti-AZ、Aurora Replica、Aurora Serverless v2では保護範囲が足りません。別リージョンへ継続的に複製するAurora Global Databaseが、提示された構成の中では正しいアーキテクチャです。

構成主目的リージョン障害
Aurora Replica／Multi-AZインスタンス・AZ障害への高可用性同一リージョン内のため保護できない
Aurora Serverless v2DBコンピューティング容量の自動スケーリング単独では保護できない
Aurora Global Databaseクロスリージョンの読み取り・DRセカンダリリージョンへ切替可能
レプリカラグは設定値ではありません。通信状況やワークロードによって変動する観測値です。「レプリカラグを15秒に固定する」という選択肢は成立しません。

6.2 Global Databaseの構成と切替を理解する

Aurora Global Databaseは、書き込みを受ける1つのプライマリリージョンと、最大10の読み取り専用セカンダリリージョンで構成できます。ストレージレイヤーの専用インフラで変更を複製し、クロスリージョンのレプリケーション遅延は通常1秒未満です。

計画メンテナンスなどで行うスイッチオーバーは、セカンダリを同期してから書き込み先を切り替えるためRPO 0を実現できます。一方、予期しないリージョン障害時のフェイルオーバーでは、障害時点のクロスリージョンレプリケーションラグに応じてデータ損失が発生し得ます。「通常1秒未満」は実績上の代表値であり、最大値を無条件に保証するSLAではありません。

PRIMARY REGION書き込みクラスター

通常の読み書きを処理

STORAGE REPLICATIONクロスリージョン複製

通常は1秒未満、非同期

SECONDARY REGION読み取りクラスター

障害時に書き込み先へ昇格

監視と訓練も構成の一部です。AuroraGlobalDBRPOLag、AuroraGlobalDBProgressLag、AuroraReplicaLagを監視し、エンドポイント切替、アプリ再接続、DNSやシークレット、依存サービスを含むDR手順を定期的に試験します。

出典：Aurora Global Databaseの概要、計画切替と障害復旧

6.3 「RPOを15秒に設定する」はそのまま実装できない

Aurora PostgreSQLには、Global Databaseの目標RPOを上限として追跡するクラスターパラメータ rds.global_db_rpo があります。ただし公式仕様の有効範囲は20秒以上です。したがって、設問の「RPOを15秒に設定する」は、構成の方向性は正しくても、文面どおりには実装できません。

このパラメータを設定すると、すべてのセカンダリが設定RPOを超えた場合、少なくとも1つが追いつくまでプライマリのトランザクションコミットをブロックします。データ損失上限を優先する代わりに、書き込み可用性やレイテンシへ影響する可能性があるため、値だけでなくトレードオフを設計します。

厳密なRPO 15秒が契約・規制上の必須条件なら、提示された選択肢に完全な正解はありません。Aurora Global DatabaseをDRの基盤として採用する判断は妥当ですが、「15秒を設定できる」と説明してはいけません。サービスで強制可能な最小値、実測ラグ、アラーム、復旧訓練、規制当局が求める証跡を確認し、要件と実装の不一致を設計レビューで解消します。

出典：rds.global_db_rpoの有効範囲と動作

7.1 復元先が「新規」か「既存」かで選ぶ

Auroraの復旧方法を選ぶ最初の判別軸は、元のクラスターを残して新しいDBクラスターへ復元するのか、現在のクラスターをその場で巻き戻すのかです。ポイントインタイムリカバリ（PITR）、自動バックアップ、スナップショットからの復元は、新しいDBクラスターを作成します。

バックトラックは、バックアップから新規クラスターを作るのではなく、バックトラックを有効化済みのAurora MySQL DBクラスター全体を指定時点へ巻き戻します。同じクラスターを使う要件に適合しますが、変更を破棄する破壊的なインプレース操作です。

Q13. 有効化済みAurora MySQLを、同じクラスターのまま3時間前へ戻す機能は？

7.2 72時間、対象エンジン、停止影響を正確に理解する

バックトラックはAurora MySQLの対応バージョン・対応リージョンで利用でき、Aurora PostgreSQLでは利用できません。ターゲットバックトラックウィンドウの上限は72時間です。クラスター作成時、またはスナップショットから新しいクラスターを復元するときに有効化する必要があり、無効で作成した既存クラスターへ後付けはできません。

設定したターゲットウィンドウは目標値です。書き込み量などにより実際のバックトラックウィンドウが短くなる場合があるため、対象時刻が実際の範囲内かを確認します。バックトラックは単一テーブルだけではなく、DBクラスター全体へ作用します。

無停止ではありません。処理中はAuroraがデータベースを一時停止し、開いている接続を閉じ、未コミットの読み書きを破棄します。アプリケーションからの新しい要求を停止・一時保留し、再接続と整合性確認を計画します。
バックトラックはバックアップの代わりになる？
なりません。バックトラックは短期間の操作ミスを素早く巻き戻す機能です。長期保持、クラスター消失、リージョン障害、監査用の独立した復旧点には、自動バックアップ、スナップショット、クロスリージョン保護を別途用意します。

出典：Aurora MySQLのバックトラック、バックトラックの設定

7.3 本番での安全な巻き戻し手順

  1. 障害原因を止め、バッチやアプリケーションからの新規書き込みを停止します。
  2. 影響開始時刻をUTCで特定し、実際のバックトラック可能範囲に対象時刻が含まれることを確認します。
  3. 監査・比較・フォールバック用に現時点のスナップショットや必要な証跡を保全します。
  4. 対象時刻の直前へクラスター全体をバックトラックします。
  5. クラスターの利用可能状態、データ整合性、重要な取引件数を検証します。
  6. アプリケーション接続を段階的に戻し、失敗したバッチの再実行や後続データの再処理を管理します。
時刻選定に注意：破損処理が複数トランザクションにまたがる場合、最初の不正変更より十分前を選びます。単一行や単一テーブルだけを戻したい場合は、PITRで新規クラスターを作り、比較・選択移行する方が安全なことがあります。

7.4 提示された選択肢を判定する

選択肢判定理由
PITR不正解目的時点へ戻せるが、新しいDBクラスターを作成する
Aurora Replicaを昇格不正解過去状態ではなく、プライマリに近い現在状態を引き継ぐ
Lambda＋自動バックアップ不正解復元は新規クラスターであり、独自コードでも既存へ直接上書きできない
バックトラック正解有効化済みの既存Aurora MySQLクラスターを指定時点へ巻き戻す
判別語：「過去72時間以内」「Aurora MySQL」「現在のクラスターそのもの」の3点が、バックトラックを選ぶ強い手掛かりです。

追加演習：RDS for PostgreSQLの接続暗号化

すべてのクライアントにTLSを強制するには、カスタムDBパラメータグループでrds.force_ssl=1を設定します。PostgreSQL 15以降は既定値が1、14以前は0です。rds.force_ssl自体は動的パラメータですが、新しいカスタムパラメータグループを既存DBインスタンスへ初めて関連付ける操作では再起動が必要になる場合があります。

混同しない：KMSは保存時暗号化、セキュリティグループはL3/L4の到達制御です。どちらも非TLS接続をデータベースエンジンで拒否する設定ではありません。クライアント側ではCA証明書の検証も有効にします。
