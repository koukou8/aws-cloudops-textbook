1.3 CloudFrontはドメイン名をターゲットにする

CloudFrontディストリビューションには、d111111abcdef8.cloudfront.net のようなドメイン名が割り当てられます。Route 53のエイリアスターゲットには、このドメイン名に対応するディストリビューションを選びます。

ディストリビューションIDは管理APIでリソースを識別する値であり、DNSの接続先ではありません。また、名前解決で一時的に観測したIPアドレスをAレコードへ固定してはいけません。標準構成ではサービスのドメイン名を利用します。

CloudFrontに固定IPの機能はまったくない？
CloudFrontにはAnycast Static IPsなど別要件向けの機能もありますが、通常の独自ドメイン接続で、観測したエッジIPやプライベートIPをRoute 53へ直接登録する理由にはなりません。今回の選択肢ではCloudFrontドメイン名へのエイリアスが正解です。

2.2 CloudFront側にも代替ドメイン名と証明書が必要

CloudFrontディストリビューションの代替ドメイン名（Alternate domain name）へ media.novaretail.example を追加します。HTTPSで配信するには、その名前をSubject Alternative Name（SAN）に含む有効なTLS証明書をディストリビューションへ関連付けます。

AWS Certificate Manager（ACM）の証明書をCloudFrontで使う場合は、米国東部（バージニア北部）リージョン us-east-1 で用意します。DNSだけを先に切り替えると、ディストリビューションの反映前や証明書設定の不足により正常に応答できません。

2.3 ApexとIPv6でエイリアスの価値が分かる

media.novaretail.example はサブドメインなので、標準CNAMEでCloudFrontドメイン名へ向けることも技術的には可能です。しかしRoute 53を使うなら、CloudFrontへ最適化されたエイリアスを選べます。エイリアスはゾーンApexでも使用でき、CloudFrontをターゲットにするエイリアスクエリにはRoute 53のクエリ料金がかかりません。

CloudFrontでIPv6を有効にしている場合、AエイリアスだけではなくAAAAエイリアスも同じ名前で作成します。AはIPv4、AAAAはIPv6の問い合わせに対応します。

「エイリアスは必ず高速」とは断定しません。標準CNAMEでは別名をたどるDNS処理がありますが、利用者が感じる速度はキャッシュ、リゾルバー、ネットワークなどにも左右されます。選択理由はAWS統合、Apex対応、料金、運用性で説明するのが正確です。

3.3 エイリアスとCNAMEを公平に比較する

今回の選択肢ではエイリアスAが最適です。ただし「CNAMEなら絶対に動かない」という理由ではありません。media のようなサブドメインでは、CNAMEをCloudFrontドメイン名へ向ける構成もDNS上は可能です。

Route 53エイリアスの強みは、ゾーンApexでも利用できること、CloudFront等のAWSリソースと統合されること、CloudFrontをターゲットにしたRoute 53クエリが無料であることです。独自ドメインそのものをCloudFrontの代替ドメイン名へ追加する点は、どちらのDNS方式でも変わりません。

South America（大陸コード SA）のレコードを sa-east-1 のWebサイトへ、Defaultレコードを ap-northeast-1 のWebサイトへ向けます。

位置情報ルーティングは、DNS問い合わせ元として推定した地域に基づいて応答を切り替えます。指定単位は大陸、国、米国の州です。範囲が重なる場合は、国の設定が大陸の設定より優先されるなど、より具体的な地域が選ばれます。

Route 53が地域を特定できないIPや、どの地域レコードにも一致しない問い合わせがあります。そのため「それ以外」を東京へ送る今回の構成ではDefaultレコードが必須です。Defaultを作らなければ、該当する問い合わせへRoute 53が回答を返さない可能性があります。

Q16. 正しい説明を2つ選んでください。

4.3 DNSの位置判定には限界がある

Route 53はDNS問い合わせの送信元IPを地域へマッピングします。EDNS Client Subnet（ECS）に対応する再帰リゾルバーなら利用者ネットワークの一部を判断材料にできますが、対応しない場合は再帰リゾルバーのIPが基準になります。

VPN、企業プロキシ、通信事業者のDNS構成などにより、実際の利用者の物理的な現在地と異なる判定になる場合があります。位置情報ルーティングはコンテンツ配信や地域別入口の制御に有効ですが、本人の居住地を証明する認証手段としては使いません。

可用性も必要な場合は？
地域別レコードへヘルスチェックを関連付ける設計を検討します。ただしDNSはTTLの間キャッシュされるため、即時切り替えを保証するロードバランサーではありません。地理的な振り分け、エンドポイントの冗長化、ヘルスチェック、TTLを一組で設計します。

出典：AWS公式：Geolocation routing、AWS公式：Choosing a routing policy、AWS公式：Route 53 DNS best practices

通常のCloudFrontでもエッジロケーションとリージョナルエッジキャッシュがオリジンへの到達を減らします。Origin Shieldを有効にすると、その先に共有される追加キャッシュ層が入り、異なる地域から来たキャッシュミスを一か所に集約できます。

同じオブジェクトへの同時リクエストはまとめられ、Origin Shieldからオリジンへ送る取得リクエストを最少1回まで減らせます。これにより、EC2 WebサーバーとEFSへ到達する負荷を抑えながら、CloudFront全体のキャッシュヒット率を高めやすくなります。Origin Shieldには追加料金があるため、削減できるオリジン負荷・転送量と合わせて評価します。

出典：AWS公式：Amazon CloudFront Origin Shield

Q11. EFSをマウントしたEC2オリジンへのリクエストを減らし、キャッシュヒット率も高める最適な設定は？

5.2 request collapsingは「同じキャッシュキー」で効く

CloudFrontは、同じキャッシュキーを持つ同一オブジェクトへの同時リクエストをまとめ、先頭の1件だけを次のキャッシュ層またはオリジンへ進めます。これをrequest collapsingと呼びます。Origin Shieldでは複数のリージョナルエッジキャッシュから来るリクエストも集約できます。

ただし、不要なCookie、ヘッダー、クエリ文字列をキャッシュキーへ含めると、内容が同じでも別オブジェクトとして扱われます。静的な画像やPDFでは、オリジンの応答内容を変える値だけをキャッシュキーに残すことが基本です。

設定キャッシュへの影響
不要なCookieを含める利用者ごとにキーが分裂し、ヒットしにくい
追跡用クエリをすべて含める同じ画像でも別キャッシュになりやすい
必要な値だけを許可リスト化同一コンテンツを同じキーへ集約しやすい

出典：AWS公式：キャッシュヒット率を高める／request collapsing

Q12. キャッシュヒット率を改善する行動を2つ選んでください。

5.3 TTLは「0かどうか」だけで決まらない

Minimum TTLを0秒にしても、それだけでキャッシュが無効になるわけではありません。オリジンが返すCache-Control: max-age／s-maxage、キャッシュポリシーのDefault TTLとMaximum TTLを組み合わせて実際の保持時間が決まります。Minimum・Default・Maximum TTLがすべて0ならキャッシュは無効です。

更新頻度の低い画像やPDFは、長めのs-maxageとバージョン付きファイル名を使うと、長期キャッシュと安全な更新を両立できます。反対にMinimum TTLを正の値にすると、オリジンがno-cache、no-store、privateを返しても、その最小時間はCloudFrontがキャッシュするため注意が必要です。

試験問題の読み方：「Minimum TTLを0にする」はキャッシュヒット率を高める施策ではありません。ただし「0にすると必ず即時失効する」とも限らず、オリジンヘッダーとほかのTTL設定を併せて判断します。

出典：AWS公式：キャッシュポリシーとTTL

Q13. Minimum TTLを0秒にした場合の説明として最も正確なのは？

5.4 EFSと暗号化機能を混同しない

Amazon EFSはNFSでマウントするファイルシステムであり、CloudFrontが取得に使うHTTP／HTTPSのオリジンではありません。EFS上のファイルをHTTPで返すEC2 Webサーバーをカスタムオリジンにする現在の構成は成立しています。EFSへ直接変更するのではなく、その前段のCloudFrontキャッシュを最適化します。

フィールドレベル暗号化は、クレジットカード番号など特定フィールドをエッジで公開鍵暗号化し、許可されたオリジンだけが復号できるようにする機能です。機密データ保護のための機能であり、キャッシュヒット率やオリジンリクエスト数を改善する設定ではありません。

性能・負荷の課題

Origin Shield、TTL、Cache-Control、キャッシュキーを検討

機密フィールドの保護

フィールドレベル暗号化を検討。キャッシュ改善とは別軸

追加演習：端末別配信と緊急キャッシュ更新

モバイル／デスクトップで内容を分ける

CloudFrontは既定でオリジンへ渡すUser-AgentをAmazon CloudFrontへ置換します。生のUser-Agentは値の種類が多くキャッシュ効率を落とすため、CloudFront-Is-Mobile-Viewer、CloudFront-Is-Tablet-Viewer等をキャッシュ／オリジンリクエストポリシーで必要な分だけ転送し、端末区分ごとにキャッシュを分ける方法が推奨です。

TTL満了前に改訂ページを反映する

緊急時は対象パスのCloudFront invalidationを作成し、次の要求でS3から最新版を取得させます。DNS TTLの変更ではコンテンツキャッシュは消えません。恒常的にはファイル名へバージョン／ハッシュを含め、長いTTLと安全な更新を両立します。

ApexからALBへ：Route 53では「ALIAS」という独立レコードタイプではなく、A（IPv4）／AAAA（IPv6）レコードでAliasを有効にしてALBをターゲットにします。
