1.2 「アカウント上限」だけではない：スコープを読む

AWSのクォータには適用範囲があります。「何個まで？」だけでなく、どこで数えるかを必ずセットで確認します。

スコープ例読み方
アカウント × リージョンVPC、Elastic IP、セキュリティグループ東京と大阪は別カウント
アカウント × AZNAT Gateway同じリージョンでもAZごと
VPC単位サブネット、ルートテーブル、NACLVPCごとに数える
リソース単位SGルール、ルート数SGやルートテーブルごと
グローバル一部のIAM等リージョンをまたいで共通

VPC数のクォータは、AWSアカウントごと、かつ ごとに適用されます。

1.3 既定値・適用値・引き上げ可否

DEFAULT
AWSの既定クォータ

新しいアカウント・リージョンでの標準的な初期値。

APPLIED
適用クォータ

そのアカウント・リージョンに現在適用中の値。引き上げ後は既定値と異なります。

ADJUSTABLE
調整可能か

申請できるクォータと固定クォータがあります。申請が必ず承認されるとは限りません。

運用上の正解：ドキュメントの既定値ではなく、対象アカウント・対象リージョンのService Quotas画面またはAPIで「適用クォータ」を確認します。

2.1 VPC・サブネット・CIDR・ルート

VPCクォータを上げると何が連動する？
リージョンあたりのVPCクォータを上げると、リージョンあたりのInternet Gatewayクォータも同じ値まで連動して増えます。ただし、1つのVPCへ同時にアタッチできるInternet Gatewayは1つです。

2.2 Gateway・IP・ENI

リソーススコープ既定値注意点
Internet Gatewayリージョン5VPCクォータと連動。1 VPCに1つ
NAT GatewayAZ5調整可能
Elastic IPリージョン5調整可能
Public NAT GatewayあたりEIPNAT Gateway2最大8

NAT GatewayはAZ単位：3 AZに4台ずつなら各AZは4/5で、リージョン合計12台でも既定範囲内です。
ENIは見えにくい：ロードバランサー、RDS、LambdaのVPC接続など、マネージドサービスもネットワークインターフェイスを作ります。

実務編

実務

3.1 CloudFormation失敗時の切り分け

最初にスタックイベントの最初のCREATE_FAILEDを探します。後続の「キャンセル」「ロールバック」は結果であり、根本原因ではないことが多いためです。

AWS::EC2::VPC CustomerVpc CREATE_FAILED
Resource handler returned message: "The maximum number of VPCs has been reached."

次のカードを、正しい調査順に並べ替えてください。矢印ボタンでも操作できます。

  • Service Quotasで現在の適用値と使用状況を確認する
  • CloudFormationのスタックイベントで最初の失敗を探す
  • 不要リソース削除・設計変更・引き上げ申請から対処を選ぶ
  • 対象アカウント、リージョン、AZ/VPC等のスコープを確定する
  • 失敗した論理リソースとAWSサービスのエラーを読む

順番を変更すると自動判定します。

3.2 Console・CLIで確認し、引き上げを申請する

  1. Service Quotasを開き、サービス（Amazon Virtual Private Cloud）を選ぶ。
  2. 対象リージョンを合わせ、クォータ名、適用値、調整可能か、利用率を確認する。
  3. 調整可能なら希望値を申請する。必要日より前に申請し、承認状況を追う。
  4. 承認後に適用値を再確認し、CloudFormationを再実行する。
# 1. Amazon VPCの適用クォータ一覧から、名前・値・QuotaCodeを取得
aws service-quotas list-service-quotas \
  --service-code vpc \
  --region ap-northeast-1 \
  --query 'Quotas[].{Name:QuotaName,Value:Value,Code:QuotaCode,Adjustable:Adjustable}' \
  --output table

# 2. 一覧で得たQuotaCodeを使って引き上げを申請
aws service-quotas request-service-quota-increase \
  --service-code vpc \
  --quota-code <QUOTA_CODE> \
  --desired-value 20 \
  --region ap-northeast-1
注意：クォータ引き上げは即時・自動承認とは限りません。また、IAM権限、OrganizationsのSCP、実サービス固有の制約はService Quotasとは別レイヤーです。

3.3 上限に強い設計と運用

デプロイ前
  • IaCの追加数を見積もる
  • 適用値と現在使用量を確認
  • 障害時の再作成余力を残す
  • 必要なら早めに引き上げ申請
継続運用
  • 使用率を定期監視する
  • 不要なEIP・ENI・SG等を整理
  • アカウント／リージョン別に台帳化
  • 増加傾向から先に容量計画

顧客ごとにVPCを作るべきか：強いネットワーク分離が必要なら有効ですが、顧客数に比例してVPC、サブネット、NAT Gateway、EIP、ルート、ログ、コストが増えます。共有VPC、共有サービスVPC、別アカウント化なども、分離要件・運用負荷・障害影響範囲と合わせて検討します。

総合演習

ケース：次の取引先3社を安全に追加する

東京リージョンにVPCが5個あり、適用クォータも5です。新たに3社分のVPCを同じテンプレートで追加予定です。各VPCは3 AZ、各AZにPublic NAT Gatewayを1台作ります。現在、対象の各AZにはNAT Gatewayが4台ずつあります。

VPC：5 + 3 = 8。現状の適用クォータ5を超えます。

NAT Gateway：各AZで4 + 3 = 7。各AZの既定クォータ5を超えます。

結論：VPCだけを引き上げても不十分。テンプレートが作る全リソースを、正しいスコープで事前確認する必要があります。
