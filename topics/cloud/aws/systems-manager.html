AWS運用管理基礎応用実務

AWS Systems Manager

EC2群へ同じルールでパッチを適用し、必要なエージェントを配布して、その状態を保つ。サーバー群の運用をまとめて管理するSSMの仕組みを学びます。

2つの運用課題から学ぶ

OSパッチはPatch Manager、任意ソフトウェアの継続配布はDistributor＋State Managerです。

Patch Managerでパッチの選定と準拠状況を管理します。サードパーティ製エージェントはDistributorでパッケージ化し、AWS-ConfigureAWSPackageを使うState Manager関連付けで、タグに一致するLinuxノードへ継続的に適用します。

この教材で学べること

  • Systems Managerの主要機能を、用途に応じて選び分ける。
  • 管理対象ノードの前提条件と、パッチ選定・実行・再起動の関係を説明する。
  • 80台の段階適用、継続運用、適用状況のレポートを設計する。
  • DistributorとState Managerを組み合わせ、ソフトウェアの導入・更新状態を維持する。

基礎編

基礎

1.1 Systems Managerとは

AWS Systems Managerは、EC2やオンプレミス、他クラウドのサーバーをまとめて管理するサービスです。略称はSSMです。正式名称は複数形の「Systems Manager」で、APIやエージェント名には今もSSMという名前が使われています。

80台へ1台ずつログインする代わりに、タグなどで対象を選び、コマンド実行、パッチ適用、設定の維持、情報収集をまとめて行います。ノードとは管理対象のサーバーを指し、SSMと通信できるようになったものを「管理対象ノード（managed node）」と呼びます。

01 対象を選ぶApplicationタグ

例：BatchAggregationに属する80台を指定

02 指示するSystems Manager

権限と手順に従い、実行を制御

03 実行する各ノードのSSM Agent

OS上でコマンドやパッチ処理を実行

04 確かめる実行結果・準拠状況

失敗、未適用、再起動待ちを確認

1.3 管理対象になるための前提条件

AGENT

SSM Agentが動作

対応するOSにエージェントを入れ、起動・更新します。AMIに入っていても動作確認は必要です。

IAM

ノードの権限

インスタンスプロファイルなどでSSMに通信する権限を付与します。操作者のIAM権限も別に必要です。

NETWORK

通信経路

HTTPS 443でSSM等へ到達させます。インターネット経路またはVPCエンドポイントを使います。

インスタンス単位で設定する場合は、IAMロールにAmazonSSMManagedInstanceCoreなど必要なポリシーを付け、インスタンスプロファイルを関連付けます。別の方法として、条件を満たすEC2をアカウント・リージョン単位で管理するDefault Host Management Configurationもあります。

主な通信先は ssm と ssmmessages です。エージェントやリージョンによって旧来の ec2messages も確認します。SSMとの接続ができても、OSのパッケージリポジトリや必要なS3領域へ到達できなければパッチ処理は失敗します。

同じAMIでも同じ管理状態とは限りません。起動後のIAMロール、サブネットの経路、Agentの停止などで差が出ます。まず80台すべてが管理対象として認識され、接続できるかを確認します。

2.1 「何を・誰に・いつ・どう実行するか」を分ける

決めること仕組み例
何を適用するかパッチベースライン対象OS、Security分類、重要度、承認までの日数、承認・拒否リスト
誰へ適用するかタグ、ノードID、リソースグループApplication=BatchAggregation のノード群

パッチベースラインは、パッチを承認するためのルールです。EC2のAMIやバックアップではありません。OSごとに、どの分類・重要度をいつ承認するかを設定します。OSごとに使えるフィルターや承認ルールは異なります。

Applicationタグは実行対象の選択に使えますが、そのタグだけでカスタムベースラインが自動的に選ばれるわけではありません。従来方式で既定以外のベースラインを使う場合は、PatchGroup（または Patch Group）という専用タグのグループをベースラインへ関連付けます。パッチポリシー方式では、ポリシー内でOSごとにベースラインを選べます。

「今すぐパッチを適用」なら、公開直後のパッチも入る？
「今すぐ」は実行時刻の指定です。ベースラインの承認条件は引き続き適用されます。たとえば公開7日後に承認するルールでは、公開直後の更新が対象にならない場合があります。緊急時は承認ルールや明示的な承認リストも確認します。

2.2 Patch ManagerとRun Commandはどう関係する？

Patch Managerは、パッチのルールと準拠状況を扱います。Run Commandは、コマンド型のSSMドキュメントをノードへ実行する仕組みです。Run Commandから AWS-RunPatchBaseline を呼び出して、Patch Managerのルールに基づく処理を実行できます。

SSMドキュメントは、実行する手順とパラメーターをJSONやYAMLで定義したものです。AWS-RunShellScript は任意のシェルコマンド、AWS-RunPatchBaseline はベースラインに従うパッチ処理に使います。自作スクリプトで更新する方法にも用途はありますが、承認ルール・準拠状況・レポートまで必要ならPatch Managerを軸にします。

方式使いどころ押さえる点
Patch now今回の緊急適用や単発のScan1アカウント・1リージョンの対象を選び、その場で開始
Maintenance Windows決めた保守時間内で定期実行時間帯・対象・タスクを設定。Run Commandタスク等を登録
Quick Setupのパッチポリシー継続運用、複数アカウント・リージョンの統一管理OS別のベースライン、ScanとInstallのスケジュールをまとめて設定
設問と現在の実務：画像では「Patch Manager＋即時適用＋Maintenance Windows」が適切です。現在AWSは継続的な設定にはパッチポリシーを推奨しています。Patch nowはパッチポリシーを直接実行する操作ではなく、別のオンデマンド経路です。複数の経路を併用する場合は、使用ベースラインの違いに注意します。

出典：SSM Documents、Patch now、Quick Setupのパッチポリシー

2.3 80台で体験する：Scan → Install → 再確認

Scanは不足する承認済みパッチを調べ、準拠状況を報告します。パッチのインストールや再起動は行いません。Installは承認済みで対象ノードに必要な更新を適用します。

再起動が必要な更新では、インストールしただけで変更が有効になるとは限りません。NoRebootは再起動を後回しにする設定です。再起動とその後の状態確認までを作業計画に含めます。

0準拠
0未適用
0再起動待ち
80未評価

緑＝準拠／橙＝未適用／青紫＝再起動待ち／灰＝未評価。各タイルの説明にも状態を表示します。

3.1 DistributorとState Managerの役割を分ける

サードパーティ製の監視エージェントは、OSパッチではありません。インストーラー、対応OS・CPU、インストール／アンインストール手順、バージョンをDistributorパッケージとして管理します。Distributorは「何を配るか」を担当します。

そのパッケージを、どのノードへ、いつ、どの状態になるよう適用するかはState Managerの関連付けで定義します。関連付けが実行するAWS管理ドキュメントは AWS-ConfigureAWSPackage です。つまり、Distributorだけを作っても自動配布は始まらず、State Managerだけでは配布物のライフサイクル管理が不足します。

01 PACKAGEDistributor

実行ファイル、スクリプト、マニフェスト、バージョン

02 DESIRED STATEState Manager

関連付け、タグ、スケジュール、レート制御

03 EXECUTEAWS-ConfigureAWSPackage

Install／Uninstall、完全再導入／インプレース更新

04 TARGETLinux管理対象ノード

既存ノードと、後からタグ条件を満たす新規ノード

機能できること今回の位置付け
Distributorパッケージ作成、対応プラットフォーム、ハッシュ、バージョンの管理セキュリティエージェントを配布可能な形にする
State Manager関連付けを対象へ即時・定期適用し、望ましい状態を維持タグ対象へインストールと更新を繰り返す
Inventoryインストール済みアプリケーションなどの構成情報を収集確認には使えるが、配布はしない
OpsCenter / OpsItem運用上の問題を記録し、調査・対応を追跡チケット管理であり、配布はしない
Run Commandドキュメントやスクリプトを一度実行単発導入には使えるが、状態維持はState Managerが適切

出典：Systems Manager Distributor、State Managerの仕組み

Q11. 正しい役割分担は？

3.2 パッケージ化と更新方式を設計する

Linux向けの高度なパッケージ作成では、インストーラーと install.sh、uninstall.sh をZIPにまとめ、対応プラットフォーム・アーキテクチャ・ファイルのSHA-256・パッケージバージョンをJSONマニフェストへ記述します。コンソールのSimpleワークフローでは、インストール／アンインストールスクリプトやハッシュ、マニフェストを生成できます。

更新方式は可用性に直結します。既定の Uninstall and reinstall はいったん旧版を削除して再導入するため、その間エージェントは停止します。In-place update は新規・変更ファイルだけを更新でき、アプリケーションを稼働させたまま更新できますが、パッケージに update.sh を用意する必要があります。ベンダーの対応手順を検証し、無条件にインプレース更新へ切り替えないようにします。

VERSION

更新版を追加

人が判別できるバージョンを付け、旧版も追跡できるようにします。

LATEST OR PIN

追従か固定か

Versionを省略すれば最新公開版、指定すれば検証済みの特定版を導入します。

ROLLBACK

戻し方も検証

旧版への再導入、サービス再起動、設定ファイルの互換性を事前確認します。

「最新版を公開したら即時に全台更新」とは限りません。State Managerは関連付けの作成・更新、対象ノードの追加、スケジュール、手動実行などを契機に動きます。緊急更新は新バージョンを登録した後、検証対象で確認し、関連付けを手動実行または更新して段階的に広げます。
AWS-RunRemoteScriptではなぜ不十分？
AWS-RunRemoteScriptはS3やGitHub上のスクリプトを取得して実行する汎用ドキュメントです。独自処理には便利ですが、Distributorのパッケージバージョンやインストール／アンインストール処理を直接扱うものではありません。Distributorパッケージの導入・更新には、専用のAWS-ConfigureAWSPackageを選びます。

出典：Distributorパッケージの作成、パッケージバージョンの追加、パッケージの導入・更新

Q12. すべてのLinux EC2へ監視エージェントを導入・更新する最小運用の手順を2つ選んでください。

3.3 タグで既存・新規ノードへ継続適用する

State Manager関連付けのTargetに、たとえば Platform=Linux といったタグ条件を指定します。CommandまたはPolicyドキュメントを使う関連付けでは、後から条件に一致する新しい管理対象ノードが追加されると、State Managerが関連付けを自動適用し、既定ではすぐに実行した後、設定したスケジュールでも実行します。対象タグを外すと、そのノードは以後の実行対象から外れます。

関連付けはアカウントとリージョンの範囲で考えます。複数リージョンや複数アカウントへ広げる場合は、それぞれに設定を展開するか、Systems Manager Quick SetupでDistributorパッケージを組織へ展開します。パッケージを別アカウントで更新しても、他アカウントの関連付けが自動実行されるわけではありません。

# 学習用の構成例。実環境のパッケージ名・タグ・間隔へ置換
aws ssm create-association \
  --name AWS-ConfigureAWSPackage \
  --parameters '{"action":["Install"],"installationType":["In-place update"],"name":["SecurityAgent"]}' \
  --targets 'Key=tag:Platform,Values=Linux' \
  --schedule-expression 'rate(1 hour)' \
  --max-concurrency '10%' \
  --max-errors '1' \
  --region ap-northeast-1
設定目的実務上の確認
タグターゲットインスタンスIDの列挙をなくすキー・値・大文字小文字と、タグ付与の自動化
スケジュール欠落や更新を定期的に是正速やかな展開要件に合う間隔、重複実行の回避
Concurrency同時更新台数を制限検証タグ→少数本番→全体の順で段階展開
Error threshold失敗時に新たな配信を止める自動ロールバックではないため、復旧手順を別に用意
実行状態・出力成功、失敗、未到達を把握Association historyと対象台帳を照合
前提条件を忘れない：タグが付いていても、SSM Agent、ノード用IAM権限、SSMとパッケージ取得先へのHTTPS経路がなければ実行できません。また、関連付けを作成できる主体は対象ノード上で高い権限の処理を実行できるため、最小権限で管理します。

出典：State Managerのターゲットとレート制御、タグ対象へのパッケージ配布、Quick Setupによる組織展開

実務編

実務

4.1 80台へ適用する運用を組み立てる

まずタグと対象台数を突き合わせ、SSMから全台を管理できる状態にします。次にOSに合うベースラインを決め、Scanで現状を調べます。検証用ノードと本番の少数台で動作を確認してから、残りへ広げます。

バッチ処理を実行中なら、新規ジョブの受付停止や実行中ジョブの完了待ちを手順に入れます。再起動の可否、失敗時の復旧方法、更新前のバックアップも決めます。同じAMIから構築されていても、検証を省略する根拠にはなりません。

同時実行数

Maintenance WindowsのRun Commandタスク等ではMaxConcurrencyを台数・割合で指定できます。たとえば10%は80台中およそ8台を上限にする設定です。

エラーしきい値

MaxErrorsで、新たな対象への配信を止める目安を指定します。すでに実行中の処理は完了することがあり、失敗数の厳密な上限や自動ロールバックではありません。

Patch nowとの違い：Patch nowの同時実行数とエラーしきい値はPatch Managerが管理します。細かな実行制御が必要ならMaintenance Windows等の対応する経路を選びます。保守時間の終了も、実行中の更新を必ず強制停止する保証にはなりません。

出典：Run Commandの対象とレート制御、Patch nowの実行制御

4.2 各インスタンスの適用状況をレポートする

「コマンドが終了したか」と「必要なパッチが入ったか」は、確認する情報が異なります。実行結果で失敗やタイムアウトを調べ、Patch Managerのコンプライアンス情報でノードごとの不足・失敗・再起動待ちを確認します。最後にバッチ処理が正常に動くかを確かめます。

準拠（Compliant）は、使用したベースラインの基準を満たすという意味です。すべての脆弱性がないことを保証する状態ではありません。レポートを見る際は、対象台数、評価時刻、使用ベースラインをセットで記録します。

確認項目判断すること
インスタンスID・対象タグ期待した80台が集計対象に含まれているか
Missing / Failed承認済みパッチの不足やインストール失敗があるか
InstalledPendingReboot変更を有効化するための再起動が残っていないか
評価時刻・ベースラインID今回の作業で、意図したルールを使った結果か
未報告・通信不能ノード成功したノードだけを見て完了と誤認していないか
レポートはCSVとして残せる？
Patch ManagerのCompliance reportingからS3へCSV出力できます。全ノード向けはノード別の非準拠パッチ数などの集計、単一ノード向けはパッチ名やIDまでの詳細を扱います。レポート出力は単発またはスケジュール設定が可能です。出力先S3やKMSの権限も設定します。
# 管理対象ノードと接続状態を確認（参照操作）
aws ssm describe-instance-information --region ap-northeast-1

# 1台のパッチ集計を確認。IDは実環境の値へ置換
aws ssm describe-instance-patch-states \
  --instance-ids i-0123456789abcdef0 \
  --region ap-northeast-1

# Run Commandで実行した処理のノード別結果を確認
aws ssm list-command-invocations \
  --command-id <COMMAND_ID> --details \
  --region ap-northeast-1
レポートはその時点の状態です。最新の成功したScan等が準拠情報を更新します。別ベースラインで手動Scanすると以前の結果を上書きすることがあるため、ベースラインIDと取得時刻を確認してください。未報告ノードはEC2の対象台帳とも照合します。

4.3 よくある失敗と、調査時の接続

症状主な確認箇所
SSMにノードが表示されない対象アカウント・リージョン、Agentの動作、ノード権限、DNS・HTTPS経路
80台の一部だけ対象にならないタグのキー・値・大文字小文字、ノードの登録状態、実行時のターゲット条件
Scan成功だが更新されないScanは検査のみ。Installを実行したか、更新が承認条件に合うか
更新の取得に失敗するリポジトリや必要なS3への経路、OSのサポート状況、実行ログ
インストール後も非準拠失敗パッチ、再起動待ち、ベースラインの違い、評価時刻

ノード内での調査にはSession Managerを使えます。対話的な接続にも、実行者のIAM権限、SSM Agent、ノードの権限と通信経路が必要です。ノードへのインバウンド22番ポートを開く必要はありません。

通常のシェルセッションの入出力は、設定によりCloudWatch LogsやS3へ保存できます。CloudTrailのAPI操作記録と、シェルで実行した内容の記録は別です。また、ポートフォワーディングやSSHトンネルのセッション内容は記録できません。

総合演習：今回の設問を解く

80台・今後も自動化・各ノードのレポート

問題は、OSパッチの今回の自動適用、今後の作業自動化、インスタンス別の適用状況レポートを求めています。この3つをまとめて扱う中心機能がPatch Managerです。

選択肢判断理由
1. 自作スクリプト＋Run Commandを都度実行最適ではない単発実行は可能ですが、今後の定期適用・承認管理・レポートを追加設計する必要があります。
2. Run Commandでベースラインを作成誤りベースラインの管理主体とPatch nowの機能が不正確です。Run Commandは実行機能です。
3. Patch Manager＋Patch now＋Maintenance Windows正解パッチ選定、今回の適用、今後の定期実行を組み合わせ、準拠レポートも取得できます。
4. 1台ずつSSHし、手動で記録要件を満たさない継続的な自動化と集中管理の要件に合いません。
選択肢3を実装するときの補足：Applicationタグは80台の実行対象を選ぶために使います。カスタムベースラインを選ばせる従来方式では、別途 PatchGroup タグとベースラインの関連付けが必要です。「全インスタンスへ即時適用」は今すぐ処理を開始する意味で、80台を同時に再起動する意味ではありません。定期実行後も、失敗や未報告ノードへの対処は必要です。
試験解答と現在の推奨構成を分ける：提示された選択肢では、Patch Manager、Patch now、Maintenance Windowsを組み合わせる3番目が正解です。一方、現在AWSは継続的なパッチ運用にQuick Setupのパッチポリシーを推奨しています。特に複数アカウント・複数リージョンでは、ScanとInstallのスケジュール、OS別ベースライン、対象範囲を一元設定できるパッチポリシーを優先して検討します。

Q10. 要件を最も直接的に満たす構成は？

全Linux EC2・監視エージェント・更新版を速やかに展開

この設問は「配布物を管理する仕組み」と「望ましい状態を継続適用する仕組み」を2つ選ばせています。正解は、サードパーティ製エージェントのDistributorパッケージを作成し、AWS-ConfigureAWSPackage を使うState Manager関連付けをLinuxタグ対象で作成する組み合わせです。

選択肢判断理由
Lambdaで各インスタンスへログイン不正解接続、認証、再試行、対象発見を自作するため、管理負荷が増えます。
Distributorパッケージを作成正解導入物、スクリプト、対応環境、バージョンを一元管理できます。
OpsItem＋Inventory不正解OpsItemは問題追跡、Inventoryは構成収集であり、ソフトウェアを配布しません。
AWS-RunRemoteScriptを関連付け不正解任意スクリプトの実行用で、Distributorのパッケージ管理とは統合されません。
AWS-ConfigureAWSPackage＋タグ対象正解Distributorパッケージの導入・更新に特化し、新しい対象ノードにも継続適用できます。
試験解答から実装へ：本番ではタグ付与の強制、検証用の対象グループ、同時実行数、エラーしきい値、更新方式、バージョン固定／最新版追従、ロールバックを追加設計します。Inventoryは正解の代わりではありませんが、導入後の確認材料として併用できます。
