基礎編

基礎

1.1 VPCフローログとは

VPCフローログ（VPC Flow Logs）は、VPC内のネットワークインターフェイス（ENI）を出入りするIP通信の情報を収集するAWS機能です。対象にはVPC全体、サブネット、個別ENIを選べます。VPCまたはサブネットを対象にすると、配下のENIがまとめて監視されます。

01 CAPTURE
ENIで観測

IPフローのメタデータを収集

02 AGGREGATE
時間窓で集約

同じフローを1行へまとめる

03 PUBLISH
保存先へ配信

CloudWatch Logs / S3 / Firehose

大事な見方：フローログはパケットキャプチャではありません。HTTP本文、SQL、認証トークンなどのペイロードは記録せず、通信のメタデータを記録します。収集は通信経路の外側で行われるため、ネットワークのスループットやレイテンシーには影響しません。
Q1. VPCフローログが主に記録するものはどれですか？

1.2 1行は「通信フロー」の要約

標準形式はスペース区切りで、バージョン2の14フィールドを持ちます。中心となるのは送信元IP、宛先IP、送信元ポート、宛先ポート、プロトコルという5つの組み合わせ（5-tuple）です。同じENI上の同じフローを集約期間ごとに1レコードへまとめます。

観点代表フィールド読み取れること
どこでinterface-id観測したENI
誰から誰へsrcaddr / dstaddr送信元・宛先IP
何の通信srcport / dstport / protocolポートとIPプロトコル番号
どれだけpackets / bytes集約期間内のパケット数・バイト数
どうなったaction / log-status許可・拒否、記録状態

送信元IP・宛先IP・送信元ポート・宛先ポートと組み合わせる5つ目の要素は、IP です。

1.3 ACCEPT / REJECTを正しく読む

ACCEPT

観測地点のセキュリティグループやネットワークACLなどで、通信が許可されたことを示します。ただしアプリケーションが正常応答した保証ではありません。

REJECT

通信が拒否されたことを示します。REJECTという1語だけで、どのルールが原因かまでは特定できません。周辺設定との照合が必要です。

よくある誤解：ACCEPTなら接続成功？
いいえ。ACCEPTでも、アプリが待ち受けていない、OSファイアウォールで止まる、応答経路がない、TLSで失敗する、といった問題は残ります。フローログは「ネットワーク調査の重要な証拠」であって、単独で全原因を説明するログではありません。

応用編

応用

2.1 ログを実際に分解する

次の標準形式のサンプルを編集し、「解析する」を押してください。プロトコル番号6はTCP、17はUDP、1はICMPです。時刻はUnix秒で記録されます。

Q3. 初期表示のサンプルから読み取れる内容をすべて選んでください。

2.2 対象・トラフィック種別・保存先を選ぶ

作成時には「どのリソースを見るか」「ACCEPT / REJECT / ALLのどれを収集するか」「どこへ配信するか」を決めます。最適解は目的によって変わります。

CloudWatch Logs

Logs Insightsで素早く検索し、メトリクスフィルターやアラームへつなげやすい選択です。

Amazon S3

長期保管や大量分析に向きます。Parquet形式とAthenaを組み合わせると効率的です。

Data Firehose

ストリーミング配信や外部分析基盤への中継など、継続的なパイプラインに向きます。

設計のコツ：ALLを永久に保存する？
ALLは調査材料が多い一方、ログ量と費用も増えます。調査速度が重要なワークロードはCloudWatch Logs、長期監査や横断分析はS3というように、保持期間と分析目的を先に決めましょう。必要なら複数のフローログサブスクリプションを目的別に作れます。
Q4. 1年分を低コスト寄りに保管し、必要時にAthenaで分析したい場合の第一候補は？

2.3 集約期間と配信遅延

最大集約期間は通常1分または10分から選びます。1分は調査の粒度が上がる一方、レコード数が増えます。Nitroベースのインスタンスへ接続されたENIでは、設定値にかかわらず集約期間が1分以下になる場合があります。

リアルタイムではありません。 収集後に処理と配信の時間が必要です。AWS公式では通常の目安としてCloudWatch Logsは約5分、S3は約10分とされていますが、配信はベストエフォートで、さらに遅れることがあります。
Q5. 最大集約期間を10分から1分へ短くしたときの一般的な影響は？

2.4 カスタム形式と、記録されない通信

カスタム形式では必要なフィールドだけを選び、順序も指定できます。NATやEKSなど中間レイヤーがある環境では、pkt-srcaddr / pkt-dstaddr、方向を示すflow-directionが役立ちます。

記録されない代表例
  • Amazon提供DNSへの問い合わせ
  • インスタンスメタデータ（169.254.169.254）
  • Amazon Time Sync Service
  • DHCP、ARP、既定VPCルーターの予約IP
品質上の注意
  • 一部レコードがSKIPされる可能性
  • 配信遅延が発生する可能性
  • 非該当フィールドは「-」になる
  • メタデータ系フィールドはベストエフォート
Q6. 通常、VPCフローログに記録されない通信をすべて選んでください。

実務編

実務

3.1 最初の運用設計

本番環境では「とりあえず有効化」で終わらせず、調査目的、対象、保持期間、アクセス権、費用をセットで決めます。次の順序で設計すると抜け漏れを減らせます。

  • 収集対象とACCEPT / REJECT / ALLを決める
  • 障害調査・監査・分析などの目的を決める
  • クエリ、アラート、費用を定期レビューする
  • 必要な時間粒度と保持期間を決める
  • 配信先、暗号化、閲覧権限を設定する

カードをドラッグして、設計の流れに並べ替えてください。

実務の初期案
重要VPCはALLで可視化し、調査用はCloudWatch Logsに短〜中期保存、長期保管はS3に集約する構成が考えられます。ただし、ログ量と保持要件は組織ごとに異なります。目的のない全量・長期保存は避け、ライフサイクルポリシーも設定しましょう。

3.2 接続できないときの調査手順

STEP 1
観測点を特定

対象ENIと通信方向を確認

STEP 2
時間を絞る

事象時刻の前後を検索

STEP 3
フローを絞る

IP・ポート・actionで抽出

STEP 4
周辺設定と照合

SG・NACL・経路・OS・アプリ

CloudWatch Logs Insights例（標準形式をparse）
fields @timestamp, @message
| parse @message "* * * * * * * * * * * * * *"
  as version, accountId, interfaceId, srcAddr, dstAddr,
     srcPort, dstPort, protocol, packets, bytes,
     startTime, endTime, action, logStatus
| filter interfaceId = "eni-0abc123def456"
| filter dstPort = 443 and action = "REJECT"
| sort @timestamp desc
| limit 50
戻り通信も確認：片方向の行だけで結論を出さず、逆方向のフロー、TCPフラグ、別ENIのログも見ます。NAT Gatewayやロードバランサーを通ると観測点が増えるため、各ホップを追う意識が重要です。
Q7. 443番へのフローがACCEPTなのに接続できません。次に確認すべきものは？

3.3 セキュリティ監視とコスト管理

監視の例
  • 管理ポートへのREJECT急増
  • 想定外の外向き宛先やポート
  • 大容量のegress
  • 既知の通信パターンからの逸脱
費用の抑え方
  • 目的に合わせてフィールドを選ぶ
  • ログ保持期間を設定する
  • S3ではParquetとパーティションを使う
  • クエリ対象期間と列を絞る

フローログの公開には、vended logsの取り込み・保存などに料金がかかります。アラートは単一イベントだけでなく「一定時間の増加率」や「通常との差」で設計すると、ノイズを抑えやすくなります。

Q8. コストと安全性を両立する施策をすべて選んでください。

総合演習

ケース：WebサーバーのHTTPSに接続できない

利用者のIPは203.0.113.10、Webサーバーは10.0.2.80です。対象ENIのログには、203.0.113.10 → 10.0.2.80:443のREJECTが記録されています。アプリケーションログには到達記録がありません。

考える順序：まずREJECTがネットワーク層の手掛かりであることを確認し、対象ENIのセキュリティグループ、サブネットのネットワークACL、適用対象と通信方向を照合します。
Q9. 最初の切り分けとして最も適切なのは？
模範的な調査メモ
1) 事象時刻とENIを確定、2) src/dst/port/actionで対象行を抽出、3) 同時間帯の戻り通信も確認、4) SGのインバウンド443と送信元条件を確認、5) NACLの受信443と戻り用エフェメラルポートを両方向で確認、6) ACCEPTに変わった後も失敗するならOS・待ち受け・TLS・アプリログへ進む、という流れです。

追加演習：ログが見えない場合とステートレスACL

Activeなのにロググループがない

CloudWatch Logs宛てでは、対象ENIでトラフィックが記録されて初めてロググループ／ストリームが作られます。作成直後は10分以上かかる場合もあるため、接続テストで通信を発生させ、配信を待ってからIAM配信ロールを確認します。

出典：VPC Flow Logsのトラブルシューティング

HTTP要求は入るが応答が戻らない

セキュリティグループはステートフルですが、ネットワークACLはステートレスです。カスタムNACLでインバウンドTCP/80だけを許可しても、クライアントのエフェメラルポート宛てのアウトバウンド応答が拒否されれば接続は成立しません。OSの実際の範囲を確認して双方向を許可します。

Q10. Activeなフローログのロググループが見えない主な理由を2つ選んでください。
