AWS WAF — XSSの緊急緩和と恒久対策

Webリクエストをレイヤー7で検査し、XSSなどの攻撃を入口で緩和します。同時に、WAFをコード修正の代わりにしないための境界も学びます。

今回の設問の結論

速やかな緩和にはAWS WAFを導入し、XSSを検出するルールをWeb ACLへ追加して、CloudFrontやALBなどの入口へ関連付けます。

AWS Managed RulesのCore rule set（AWSManagedRulesCommonRuleSet）には、リクエスト本文、Cookie、クエリ引数、URIパスなどの一般的なXSSパターンを検査するルールがあります。緊急遮断と並行して、保存済みデータの除去、文脈に応じた出力エンコード、HTMLサニタイズなどの恒久修正を進めます。

重要：AWS WAFは攻撃リクエストを入口で緩和する防御層です。アプリケーションのXSS脆弱性そのものを修正したり、すでにデータベースへ保存された悪意ある投稿を自動削除したりはしません。

出典：AWS WAFとは、AWS Managed Rules — Core rule set

この教材で学べること

  • 格納型・反射型・DOM型XSSの違いと影響を説明する。
  • Web ACL、ルール、ルールグループ、優先順位、アクションを区別する。
  • CloudFront・ALB等へAWS WAFを関連付け、XSSルールを段階導入する。
  • COUNT、ログ、ラベル、スコープダウンで誤検知を調整する。
  • WAFによる緩和と、出力エンコード等の恒久対策を使い分ける。

基礎編：XSSとAWS WAFの役割

基礎

1.1 XSSは「信頼できないデータを実行可能な形で出力する」問題

INPUT悪意ある投稿

スクリプトを送信

STOREDBへ保存

無害化されない

OUTPUTプロフィール表示

HTMLへそのまま埋込

EXECUTE他者のブラウザ

スクリプト実行

クロスサイトスクリプティング（XSS）は、信頼できない入力がHTMLやJavaScriptの文脈へ安全にエンコードされず出力され、閲覧者のブラウザで攻撃者のスクリプトとして実行される脆弱性です。今回の投稿欄のように、攻撃文字列が保存されて別の利用者へ配信されるものを格納型XSSと呼びます。

反射型XSSではURLやフォームの値が直後のレスポンスへ反映されます。DOM型XSSではクライアント側JavaScriptのsourceからsinkへの処理だけで成立する場合があり、悪意ある文字列がHTTPリクエスト上で明確に見えなければWAFだけでは防げません。

種類典型的な流れWAFの限界
格納型投稿→DB→別利用者へ表示新規投入は緩和できるが、保存済みデータは残る
反射型URL等→直後のレスポンス既知パターンは検査可能だが回避表現がある
DOM型ブラウザ内source→危険なsinkサーバーへのリクエストだけでは見えない場合がある

Q1. 投稿欄のスクリプトが保存され、別の利用者の閲覧時に実行されました。何型のXSSに近いですか？

1.2 AWS WAFはHTTP(S)リクエストを入口で評価する

AWS WAFは、保護対象へ転送されるHTTP(S)リクエストを評価するWeb Application Firewallです。IPアドレス、ヘッダー、Cookie、クエリ文字列、URI、リクエスト本文、送信レート、XSS・SQLiのような攻撃パターンなどを条件にできます。

一致したリクエストにはAllow、Block、Count、CAPTCHA、Challengeなどのアクションを適用できます。今回の緊急緩和では、XSSルールに一致する新しい投稿リクエストをBlockすることで、アプリケーションへ到達する前に攻撃入力を減らします。

AWS WAFは各ルールを数値の小さい優先順位から評価します。BlockやAllowのような終了アクションに一致すると評価を終了し、Countは記録・ラベル付けをして次のルールへ進みます。例外ルールを上位に置く場合は、意図せず攻撃通信までAllowしないようスコープを狭くします。

Q3. ルールを優先順位付きで束ね、保護対象へ関連付けるものは？

2.2 対応する入口とスコープを確認する

Web ACLはCloudFrontディストリビューションや、リージョナルなApplication Load Balancer、API Gateway REST API、AppSync GraphQL API、Cognitoユーザープール、App Runner、Verified Accessなどの対応リソースへ関連付けます。Network Load BalancerにはWeb ACLを直接関連付けられません。

CloudFront用Web ACLとそのIP set・regex pattern set等はGlobal（CloudFront）スコープ、実体上はus-east-1で管理します。ALBなどリージョナルリソース用Web ACLは、保護対象と同じリージョンに作成します。1つの保護対象に関連付けられるWeb ACLは1つです。

入口直接関連付けスコープ
CloudFront対応Global（CloudFront）／us-east-1
ALB対応ALBと同じリージョン
API Gateway REST API対応APIと同じリージョン
NLB非対応—

3

応用編：XSSルールの選択と限界

応用

3.1 まずCore rule set、必要ならXSS match statement

AWSManagedRulesCommonRuleSetは一般的なWeb脅威に対するベースラインで、CrossSiteScripting_BODY、CrossSiteScripting_COOKIE、CrossSiteScripting_QUERYARGUMENTS、CrossSiteScripting_URIPATHなどを含みます。管理ルールは継続的に保守されるため、緊急緩和の出発点に適しています。

独自フォームやAPIに絞る場合はXSS match statementで検査対象の本文、JSON body、Cookie、ヘッダー、クエリ等を指定し、URLデコードやHTML entity decodeのようなtext transformationを順序付きで適用できます。パスやHTTPメソッドとAND条件で組み合わせれば、投稿APIだけを狙ったルールにできます。

出典：Core rule set、XSS attack rule statement

Q5. 一般的なXSSパターンを速やかに検査する開始点として適切なのは？

3.2 「検査できるリクエスト範囲」を設計する

AWS WAFが検査するのはWebリクエストです。レスポンス本文をサニタイズするプロキシではありません。さらにBody、JSON body、Headers、Cookiesには検査できるサイズの上限があり、上限を超えた部分をどう扱うかというoversize handlingをルールごとに設計します。

格納型XSSでは、WAFを導入する前に保存された悪意ある投稿はデータベースに残っています。対象レコードを特定して安全に除去し、キャッシュも無効化します。WAFのログに本文やCookie等が含まれ得るため、機密フィールドのredaction、データ保護、保存期間、アクセス権も設定します。

WAFは完全なHTMLパーサーではありません。難読化やアプリ固有の形式、クライアント側だけで成立するDOM型XSS、検査上限を超える本文などを100%防ぐ保証はありません。防御層として活用し、アプリ修正を省略しないでください。

4

実務編：速やかで安全な導入

実務

4.1 Countで観測し、緊急度に合わせてBlockへ移す

  1. 攻撃経路と保護対象を特定

    CloudFront、ALB、REST API等のどこへWeb ACLを関連付けるか確認します。

  2. Web ACLと管理ルールを追加

    Core rule setを追加し、投稿APIのパスやメソッドで必要に応じてスコープを絞ります。

  3. 短時間Countで確認

    サンプルリクエスト、CloudWatchメトリクス、ログで正常投稿が一致しないか確認します。

  4. Blockへ切り替える

    侵害が進行中なら観測時間を最小化し、対象XSSルールをBlockへ移して監視します。

  5. 例外は狭く作る

    ルール全体を無効化せず、誤検知するパス・項目・条件だけを除外します。

  6. アプリ修正とデータ調査

    根本原因を修正し、保存済み攻撃データとセッション侵害の有無を調査します。

ルールグループのアクションをCountへオーバーライドすると、遮断せず一致数とラベルを観測できます。これは誤検知の評価に有効ですが、Count中は攻撃を止めません。侵入テストで再現済みかつ悪用が疑われる場合は、影響範囲の小さいルールから速やかにBlockへ移します。

出典：AWS WAF Developer Guide — rule action override

Q7. 安全な導入順へ並べ替えてください。

  • 対象ルールをBlockへ移す
  • 保護対象と攻撃経路を特定する
  • アプリ修正と保存済みデータの調査を進める
  • ログとメトリクスで誤検知を確認する
  • Web ACLへルールをCountで追加する

ドラッグまたは矢印ボタンで変更すると判定します。

4.2 ログ・メトリクス・サンプルで調整する

各ルールとWeb ACLではCloudWatchメトリクスとサンプルリクエストを確認できます。詳細ログはCloudWatch Logs、Amazon S3、Amazon Data Firehoseへ送れます。Block数の急増、特定URI・国・IP・User-Agentへの偏り、管理ルールが付けたラベルを継続監視します。

ログには認証情報、Cookie、クエリ、個人情報が含まれ得ます。ログフィルターで必要なアクションだけを保存し、field redactionやデータ保護を設定し、KMS暗号化、最小権限、保存期間を整えます。ログ自体を新しい情報漏えい源にしないことが重要です。

観測用途
AllowedRequests / BlockedRequests全体傾向と急増を把握
CountedRequests遮断前の影響評価
Rule labelsどの管理ルールが一致したかを特定
Full logs条件調整とインシデント調査。機密情報に注意

Q8. 誤検知を安全に調整する方法を2つ選んでください。

5

恒久対策：アプリケーションでXSSをなくす

実務

5.1 WAFの後ろで修正すべきこと

最優先の根本対策

  • HTML・属性・URL・JavaScriptの文脈ごとに出力エンコード
  • HTMLを許可する投稿は信頼できるライブラリでallowlistサニタイズ
  • innerHTML等の危険なsinkを避け、安全なDOM APIを使用
  • テンプレートエンジンの自動エスケープを無効化しない

被害を抑える多層防御

  • Content Security Policy（CSP）を段階導入
  • セッションCookieへHttpOnly・Secure・SameSite
  • セッションの失効、再認証、侵害調査
  • SAST・DAST・依存関係検査と回帰テスト

入力検証は業務上許可する形式を狭めるために有効ですが、XSSの中心的な対策は「出力先の文脈に合ったエンコード」です。単純に<script>文字列を削除するだけでは、イベント属性、SVG、URLスキーム、エンコード表現などを使う回避に耐えられません。

HttpOnlyはJavaScriptからCookie値を直接読むことを難しくしますが、悪意あるスクリプトが利用者として操作することまでは止めません。CSPも強力な補助策ですが、適切なnonce／hash設計や既存スクリプトの整理が必要で、出力エンコードの代替ではありません。

6

総合演習：リリース直後に見つかった格納型XSS

新しいプロフィールページの投稿欄へ入力したスクリプトが、別の利用者のブラウザで実行されました。コード修正を待たずに攻撃入力を入口で抑え、並行して根本修正を進める必要があります。

選択肢判定理由
Elastic Load Balancing不正解負荷分散が役割。ALBはWAFの関連付け先にはなるが、ELB単独でXSS検査はしない
AWS WAF正解HTTP(S)リクエストのXSSパターンを入口で検査・Blockできる
Amazon Cognito不正解認証・ユーザーディレクトリであり、投稿本文をXSS検査しない
AWS Shield Standard不正解一般的なL3/L4 DDoS保護であり、XSS入力の検査ではない
選択問題と実務の差：選択肢の中ではAWS WAFが即時緩和の正解です。実務では、ルール適用だけで完了扱いにせず、保存済みデータの除去、セッション失効、ログ調査、コード修正、回帰テストを並行します。

Q10. このXSSを速やかに緩和するために導入すべきAWSサービスは？

覚えておく3行

  • XSSの即時緩和はAWS WAF。対応するWeb入口へWeb ACLとXSSルールを関連付ける。
  • Countとログで影響を確認し、侵害の緊急度に応じて狭い範囲からBlockへ移す。
  • WAFは根本修正ではない。保存済みデータを除去し、文脈別出力エンコードとサニタイズを実装する。
